# Backend

Load before changing `src/lib/`, colocated `_action.ts`, or gateway helpers that are not HTTP route files.

## Mandatory rules

- Domain operations live in services under `src/lib/<domain>/` (`keys/`, `tenancy/`, `reports/`, `models/`, `providers/`, `pricing/`, `settings/`, `usage/`, `rag/`, `auth/`, `gateway/request-logs/`). A service checks its permission with `requirePermission` (or `requireAuth`) first, validates its input, throws an UPPER_SNAKE error code, and returns the payload. Console pages and `/api/mgmt` handlers call the same service.
- Each page's server actions live in its colocated `_action.ts` with `"use server"` and stay thin adapters: `runAction(() => service(...args))`. They must not query Prisma or hold domain logic, and a page imports only its own `_action.ts`. Return payloads; the client applies them to `useState`.
- ESLint forbids `@/app/*` imports from `src/lib`, `src/types`, `src/schemas`, `src/worker`, and the HTTP route trees (`src/app/api`, `src/app/internal-api`, `src/app/scim`, `src/app/sso`).
- Use `runAction` / `actionFail` from `src/lib/http/action-result.ts`. User-visible action errors must be translated keys or ICU selects, not hardcoded English. Errors whose message is not an action code (`isActionCode`) become `REQUEST_FAILED` and are logged as `action.failed` with name and message only.
- Gateway request handling shares `gateRequest`, `allowModel`, `applyGuardrails`, `dispatchChat` / `streamChat`, `forwardToModel`, `meter`, `recordUsage`, and `fireAlert` under `src/lib/gateway/`. Model routes open with `screenModelRequest` (gate, body, `modelOf`, `allowModel`, `applyGuardrails`), validate with `validRequest` (`parseRequest` from `src/lib/gateway/protocols/parse-request.ts`, 400 `invalid_request`), and wrap their handler in `gatewayRoute` so every thrown error, including a rejected stream, answers through `gateResponse` (`src/lib/gateway/endpoints/pipeline.ts`). Chat and Messages dispatch route through `routeMetered`, which meters routing failures with `recordFailure`, and meter delivered responses with `recordSuccess` (`src/lib/gateway/dispatch/chat.ts`).
- Every model call runs on a request-scoped principal from `withTrace` (`src/lib/gateway/access/gate.ts`): `gateRequest` adds it for `/api/v1`, and the playground and each batch line call it themselves. The trace carries the endpoint, the guardrail-screened and PII-redacted request from `applyGuardrails(body, principal)`, the PII entities found, and the guardrail matches (`guardInput`, `guardOutput`, `guardBlocked`). Must not share one traced principal across batch lines.
- The PII and guardrail policies are always the effective ones from `resolvePolicies(principal)` (`src/lib/settings/enterprise.ts`; `resolvePii` returns its PII half): the key's override, else the key's project's, else the organization's, else the global `Enterprise.pii` / `Enterprise.guardrails`. An override replaces the whole policy. `applyGuardrails` and `writeRequestLog` must use them; must not read `getPii()` or `getGuardrails()` for request handling.
- PII mode `restore` swaps personal values for numbered placeholders from the request's `PiiVault` (`src/lib/gateway/safety/pii-vault.ts`; credentials stay un-numbered and are never restored) and puts them back only in the client answer, including batch result files (`restoreClientJson`, and for SSE `restoreClientChatStream`, `restoreClientResponsesStream`, and `restoreClientMessagesStream` in `src/lib/gateway/safety/restore-client.ts`), never in logs, caches, or stored responses, and never inside signed reasoning (`thinking`, `signature`, `encrypted_content`, `thinking_blocks`, `reasoning_details`); plain `reasoning_content` and Responses summary text are restored like answer text. Restore works on parsed JSON string values (tool `arguments` stay JSON-escaped), and unchanged stream events pass through byte-identical. The stream restorers (`restore-chat.ts`, `restore-responses.ts`, `restore-messages.ts` on `restore-sse.ts`) hold back, per choice and per content or tool-argument stream, only a trailing `[` plus up to 80 `[A-Z0-9_]` that could still become a placeholder, and flush it restored at `finish_reason`, the stream's `.done` or `content_block_stop`, `[DONE]`, or stream end; the Responses restorer renumbers `sequence_number` around held deltas. While the vault holds a value and the trace endpoint is chat completions, Responses, Messages, the playground, or a chat or Responses batch line (`needsPiiInstruction`, `src/lib/gateway/safety/pii-instruction.ts`), `dispatchChat`, `streamChat`, `dispatchMessages`, and `streamMessages` append the constant `PII_RESTORE_INSTRUCTION` to the end of the leading system or developer message (Anthropic `system`: one extra text block without `cache_control`), or add one, once per model call, so client prompt-cache prefixes stay intact. The logged request stays `trace.request`, the client's masked body without the instruction.
- Callers pass `request`, `response`, `error`, and `stream` to `recordUsage` or `meter` so the log carries content. Output screening goes through one `OutputScreen` per response (`outputScreen(outputGuard, principal.trace)`, `src/lib/gateway/safety/guardrails.ts`) passed to `screenChatJson` / `screenMessage` / `screenMessageEvent`; it runs guardrail rules before PII masking and records into the trace. A blocked response is withheld with finish reason `content_filter` (`refusal` on native Messages) and metered with outcome `guardrail_blocked`. Streams rebuild the response with `ChatStreamTranscript` / `MessagesStreamTranscript` (`src/lib/gateway/request-logs/log-content.ts`).
- MCP servers (`McpServer`, `McpAssignment`, `src/lib/mcp/`) are executed by the gateway, never passed to providers. `mcpToolsetFor` (`src/lib/mcp/toolset.ts`) resolves the caller's servers from the key tenancy chain (`chainOf`: company, department, project, person, key). The pure rule is `effectiveServers` (`src/lib/mcp/resolve.ts`): a server applies when it is `global` or has an `allow` row anywhere in the chain; a `block` row without tools anywhere in the chain removes it; `blockedTools` of every matching row and the server allowlist (`toolsRestricted`, `allowedTools`) remove single tools. Tools are injected as function tools named `mcp__<server>__<tool>` (`mcpToolName`: `[A-Za-z0-9_-]`, at most 64 characters, hash suffix when the name was changed or collides; at most 128 tools; caller tool names win).
- The MCP loop (`runMcpChat` / `streamMcpChat` in `src/lib/mcp/chat-loop.ts`, `runMcpMessages` / `streamMcpMessages` in `src/lib/mcp/messages-loop.ts`) serves chat completions, Responses without `file_search`, and Messages. Every step goes through `dispatchChat` / `streamChat` / `dispatchMessages` / `streamMessages`, so it is routed in the request's pool, output-screened, metered, and logged; every step after the first is admitted again with `admit` (with the request's `x-hub-max-cost`), and `traceStep` makes the PII-redacted step body the logged request so content logs show tool calls and results. Tool results are model input: `screenToolResult` applies the effective guardrails and PII policy and blocks with `guardrail_blocked` / `pii_blocked`, metered with that outcome. At most `MCP_MAX_STEPS` (8) model calls; the last step drops the MCP tools; tool calls share a 180-second budget with 30 seconds per call, and a failed call returns `[tool error] …` to the model instead of failing the request. A step that mixes MCP and caller tool calls returns the caller's calls and drops the MCP calls unexecuted. Responses never contain MCP tool calls; Responses add `mcp_call` items. Streaming streams every step, forwards text and caller tool calls live, withholds MCP tool-call deltas, and ends with one finish and summed usage. `X-LLMHub-MCP: off` opts out per request, `n > 1` skips MCP, and MCP requests bypass the response cache.
- `McpClient` (`src/lib/mcp/client.ts`) speaks JSON-RPC 2.0 over Streamable HTTP (2025-06-18): `initialize`, `notifications/initialized`, paginated `tools/list`, `tools/call`, `Mcp-Session-Id`, JSON or SSE answers, one re-initialize after a 404, `DELETE` on close, answers capped at 2 MB, tool text cut at 16,000 characters. Every connection uses `guardedFetch` (`src/lib/mcp/transport.ts`): `checkServerUrl` allows only https, allows http and private, loopback, and CGNAT addresses only with `McpServer.internal`, rejects credentials in URLs, and always blocks link-local and metadata addresses (169.254.0.0/16, fd00:ec2::254, metadata.google.internal); resolved addresses are checked in the socket `lookup`, so DNS rebinding cannot reach a blocked address, and redirects are not followed. Auth secrets are sealed with `seal`, opened only to build the request header, returned to the console only as `hasSecret`, and never logged; `mcp.tool_call` logs the server id, tool, duration, and an error code only.
- MCP servers are managed on the `/mcp` page through `src/lib/mcp/servers.ts` (connection tests and Reload in `server-probe.ts`, OAuth sign-in in `server-oauth.ts`, the shared row select and views in `server-view.ts`): `settings:read` or `mcp:read` views; `settings:manage` or `mcp:manage` creates, edits, tests, reloads, and assigns only in the platform scope (`requireMcpManager`, `mcpAccess` in `src/lib/mcp/scope.ts`); `mcp:install` connects a template for a company and edits access rules only on servers visible to that company; every change writes an `mcp_server.*` audit row without secrets. Cached tool lists refresh on create, on update, and from Reload, never per request.
- MCP Anything drafts a hosted server from documentation (`draftMcpServer`, `src/lib/mcp/builder.ts`). Sources are up to `MAX_BUILDER_LINKS` links, pasted text, and up to `MAX_BUILDER_FILES` uploads (10 MB each, 20 MB together, through `POST /internal-api/mcp/draft`; see [api.md](api.md)). Links may carry `bearer`, `basic`, `header`, `query`, or `cookie` (a copied browser Cookie header) auth (`loadDocsPage`, `src/lib/mcp/docs-source.ts`): it is sent only to the start link's origin (or its https upgrade, `sameSite` in `docs-login.ts`) and stripped on cross-site redirects, at most three redirects, 401/403 answer `MCP_BUILDER_FETCH_AUTH`, every fetch uses `guardedFetch` with the link's `internal` flag, and a per-link cookie jar replays same-site `Set-Cookie` (redirects included). HTML links with `crawl` (default on) are crawled breadth first by `crawlDocs` (`src/lib/mcp/docs-crawl.ts`): same site and the start URL's folder, query kept, fragment and the link's query-auth parameter dropped, `<a>`/`<area>`/`<frame>`/`<iframe>`/`<link rel=next|alternate>` with `<base href>`, never assets, sign-out, or destructive URLs (also not as redirect targets), login walls fail the start link and skip sub pages, credential values are redacted from page text, repeated navigation lines are kept once, and budgets `MAX_CRAWL_DEPTH` (8), `CRAWL_MAX_PAGES` (300, shared per draft), `CRAWL_PAGE_BYTES`, `CRAWL_TOTAL_BYTES`, `CRAWL_TIME_MS` (120 s), and `CRAWL_CONCURRENCY` (4) stop it with `truncated`. An OpenAPI document found while crawling (also Swagger UI or Redoc spec URLs on the same site) takes the import path. The builder model (`draftWithAgent`, `src/lib/mcp/builder-agent.ts`) gets `list_pages`, `read_page`, and `fetch_page` (same site as a crawled link, its login and jar, at most `MAX_FETCHED_PAGES`) for up to `MAX_AGENT_STEPS` calls per pass within `MAX_AGENT_CHARS`; a deployment that answers 400 to tools gets the plain prompt. Docs over `MAX_MODEL_DOCS` are drafted in up to `MAX_DRAFT_PASSES` passes of `PASS_DOCS_CHARS` with the site index, merged with `mergeTools`, the server head from the first pass that has one. `McpDraft.crawls`, `passes`, and `parts` report what was read. PDFs and images reach the builder model as content parts. The first OpenAPI source wins (`importedFrom`, the rest listed in `unused`). Sources, uploads, page contents, and link secrets are never stored or logged (`mcp.builder_crawl` logs counts). The review step pre-fills the server login from a same-site docs link (`docsLoginFor`); hosted servers support `basic` (user name in `authHeader`) and `query` (parameter name in `authHeader`, hosted only, applied by `hostedAuth`) besides `bearer` and `header`.
- Every model-consuming path is admitted through `admit` (`assertBudget` + `assertRate`): `/api/v1` and the playground. There is no master key and no bypass.
- `assertBudget` walks `budgetChain` (`src/lib/gateway/billing/billing.ts`): key → user → member → project → team → org; any capped holder at its cap plus active `TempBudget` boosts answers 429 `budget_exceeded`. Key tenancy is resolved live by `resolveKeyTenancy` (`src/lib/gateway/access/key-tenancy.ts`): a person key bills the member and the member's department and company, a project key bills the project and its department and company, and only an internal key (neither) bills its owning console user and that user's company; a blocked member or blocked owner makes the key inactive. Budget writes go through the budget service (`src/lib/tenancy/budgets.ts`), which rejects a cap above any capped ancestor (`capConflict` in `src/lib/utils/budget.ts`, `BUDGET_EXCEEDS_PARENT`) and allow boosts only on capped holders, for at most `MAX_BOOST_HOURS`.
- Model access is `principal.models`: the key's explicit list plus every alias its model templates match (`modelAccess`, `src/lib/gateway/access/model-access.ts`; pure matching in `src/lib/gateway/access/model-policy.ts`). A key with neither allows every alias. Routes must check the requested alias with `allowModel` and every caller fallback with `modelChain` (`src/lib/gateway/access/gate.ts`).
- Template data rules (providers, ZDR, no training, retention, region) apply per deployment: an alias matches when at least one route, also through fallback and overflow aliases, meets the rules, and `principal.routeLimits` keeps requests on those routes. Every routing call passes the limits (`withDeployment`, `forwardToModel`, `acquireGroup`); fallback and overflow groups inherit the limits of the alias the caller asked for. Aliases granted explicitly or by name rules alone stay unrestricted.
- Upstream failures throw `GateError` (`src/lib/gateway/errors.ts`) and are metered as errors. Must not fabricate responses, images, embeddings, or fallbacks when the upstream fails or lacks an endpoint.
- Provider kinds are `openai`, `anthropic`, `openrouter`, `openrouter_eu`, `xai`, `typesafe`, `openai_compat`, `moonshot` and `moonshot_cn` (Kimi API Platform, `api.moonshot.ai` / `api.moonshot.cn`), `meta` (Meta Model API key), `gemini` (Google Gemini API key), `vertex` (Google Vertex AI service account or express mode key), and the subscription kinds `codex` (ChatGPT plan), `grok_build` (SuperGrok or X Premium+), `claude` (Claude Pro or Max), `antigravity` (Google Antigravity), `kimi` and `kimi_ai` (Kimi Code on kimi.com or kimi.ai), `muse_code` (Meta Muse Code), and `devin` (Devin) (`src/lib/gateway/upstreams/provider-kinds.ts`). Provider keys are sealed in the database only; there is no env fallback. Routing strategies are `least_inflight`, `weighted_random`, `cost_lowest`, `priority`, `fast`, `round_robin`, `quota_balanced`, `quota_expiring`, and `smart` (`pickQuotaSmart`: spends quota about to reset, skips accounts at 85% or more while others have room). Deployments cool down only on retryable failures (5xx, 429, network); a 429 that names a reset (`resets_at`, `resets_in_seconds`) parks the deployment until then, at most seven days (`markFailure`).
- Google kinds (`speaksGoogle`, `src/lib/gateway/upstreams/google.ts`) translate chat natively and reuse the Antigravity converter (`chatToAntigravity`, `AntigravitySseTranslator`): chat always goes to `streamGenerateContent?alt=sse` and non-streaming answers are aggregated; Gemini 3+ effort maps to the model's `thinkingLevel`s (CLIProxyAPI's table), Gemini 2.5 to a `thinkingBudget`; call ids are stripped from history; images, audio, and files must be base64 data URLs; a `promptFeedback.blockReason` finishes as `content_filter`. `gemini` sends the key as `x-goog-api-key` and serves embeddings, images, and videos through Google's OpenAI-compatible `/openai` paths. `vertex` stores either a service account JSON (`type: service_account`, RSA key normalized to PKCS#8) or an express mode API key, sealed in `apiKey`; the base URL carries the project and location (`vertexBaseUrl`: `global`, multi-region `us`/`eu` on `aiplatform.<loc>.rep`, regions on `<loc>-aiplatform`), and the express base URL has none. Service accounts sign an RS256 assertion for `cloud-platform` and exchange it at Google's token endpoint (`src/lib/gateway/upstreams/vertex-credentials.ts`); the token is cached per provider and credential until five minutes before expiry, concurrent calls share one exchange, and a 401 from Vertex drops it. Model ids route by publisher (`vertexModelRoute`): Gemini to `publishers/google`, `claude-*` to `publishers/anthropic/…:streamRawPredict` with `anthropic_version`, `<publisher>/<model>` to `endpoints/openapi/chat/completions`, and Imagen `images/generations` to `:predict`; partner models and Imagen need a service account. Discovery lists `v1beta1/publishers/{google,anthropic}/models` (Claude as `id@version`); express mode falls back to CLIProxyAPI's Vertex Gemini list after a `countTokens` key check. The browser never receives the private key: `ProviderView.vertex` carries only credential type, service account email, project, and location.
- Subscription kinds (`auth: "sign_in"`) connect through an OAuth device sign-in from the Subscriptions tab of `/providers` (`src/lib/gateway/upstreams/subscription-sign-in.ts`); device tickets and fresh credentials travel to the browser only as sealed blobs bound to the operator and kind (add-account links bind tickets to `sub-add:<linkId>` instead, so neither side opens the other's tickets). Tokens live sealed in `ProviderLogin` and refresh under a row lease (`src/lib/gateway/upstreams/credentials.ts`); every upstream call takes its credential from `deploymentAuth` / `providerAuth`. The maintenance sweep (`sign_in_refresh`, `refreshDueLogins`) renews every active login ahead of expiry with the lead times CLIProxyAPI uses (Claude 4 h, Codex 96 h, Antigravity and Grok 30 min, Kimi 5 min before `expiresAt`; Muse keys do not expire and are only re-minted after a 401; Devin session tokens do not expire, so sign-in stores them with a far-future `expiresAt` and the sweep never picks them), never more than half the last token lifetime (`refreshedAt`), at most 16 per sweep and 4 at a time, so requests rarely refresh inline. A failed refresh records `failures` and `retryAt` (1 min doubling to 30 min, or the token endpoint's Retry-After on 429); a request inside the 5-minute skew keeps the still valid token until `retryAt` instead of retrying, and an expired token is always retried on demand. A fatal refresh answer (`invalid_grant` and similar) keeps a still valid access token in use until it expires or the upstream rejects it, and only then marks the login `expired`. Refresh writes are guarded by `version`, so a newer sign-in or import always wins. Every sign-in path (console, auth-file import, add-account link) matches an existing connection by kind, email (case-insensitive), and stored account id (`matchingConnection`, `src/lib/providers/account-match.ts`), prefers an active one, and renews it in place instead of adding a duplicate. An `expired` connection whose account is active on another connection is removed (`pruneSupersededLogins`, after each sign-in and in the sweep job `superseded_logins`, audit `provider.superseded`); it carried no traffic, so routing does not change. Their base URL is pinned to the catalog. `codex` speaks the ChatGPT Responses backend (`src/lib/gateway/upstreams/codex.ts`); its plan limits come from `subscriptionLimits` (`src/lib/gateway/upstreams/subscription-limits.ts`). Codex requests identify as `originator: llmhub`. Plan limits are never fetched for a page load or the live stream; see the subscription limit snapshots rule below. `claude` and `antigravity` sign in by pasting the callback address of a loopback redirect (`signInMethod` is `code`). `antigravity` talks to Google's Cloud Code Assist API (`src/lib/gateway/upstreams/antigravity.ts`): generation and `fetchAvailableModels` go to the daily host `ANTIGRAVITY_BASE_URL`, because the production host answers consumer accounts with 429 even with quota left, and only `loadCodeAssist` / `onboardUser` use `ANTIGRAVITY_CONTROL_URL`; `chatToAntigravity` converts chat to the `streamGenerateContent` envelope, `AntigravitySseTranslator` converts the SSE reply, `withProject` adds the Cloud project id that sign-in stores in `tokens.accountId`, per-model quota comes from `fetchAvailableModels` as windows scoped by model id and labelled with `displayName` (`src/lib/gateway/upstreams/antigravity-models.ts`: the internal `chat_*` and `tab_*` ids are dropped; discovery and the console also hide `gemini-2.5-flash-thinking` and `gemini-2.5-pro`, whose windows stay for routing; the console groups the rest by model family in `limit-groups.ts`), and `maxOutputTokens` is only sent for Claude models. The Google OAuth client secret is not in the repository: published images bundle it in `antigravity-client-secret` next to `server.js` from the `antigravity_client_secret` build secret (see [operations.md](operations.md)), and an operator can save one in the Subscriptions tab of `/providers`, sealed in `Enterprise.antigravity` (`src/lib/gateway/upstreams/antigravity-config.ts`). `antigravityClientSecret` prefers the saved secret over the bundled one, which is read once per process (trimmed; a missing or unreadable file means none), and must not move to an env var. `loadAntigravityConfig` reports `saved` and `bundled`; the tab asks for the secret only when neither exists, and with only a bundled one Google connects like the other subscriptions. Without either, `startAuthorization` answers `ANTIGRAVITY_NOT_CONFIGURED`. Cloud Code gates newer models by client version, so update `ANTIGRAVITY_CLIENT_VERSION` when Google answers 404 for a model that exists. `kimi` and `kimi_ai` use the RFC 8628 device flow of `auth.kimi.com` / `auth.kimi.ai` with the public Kimi Code client id; the domain is the kind, chosen at sign-in, and pins the API to `api.kimi.com/coding/v1` or `api.kimi.ai/coding/v1`. Sign-in generates a device id that is stored with the sealed tokens (`tokens.device`) and sent as `X-Msh-Device-Id` on refresh and every request with the other `X-Msh-*` headers (`kimiHeaders`, `src/lib/gateway/upstreams/kimi.ts`); refresh tokens rotate and a 401 or 403 from the token endpoint is fatal. Chat goes to `/chat/completions` after `kimiChatBody` (`reasoning_effort` becomes `thinking: { type, effort }`, `max` only on K3 and K2.8, temperature other than 1.0, or 0.6 with thinking disabled, is dropped, tool schemas get local `$ref`s inlined and an object root, empty assistant turns are dropped, and assistant tool-call turns without usable `reasoning_content` get the latest reasoning or a placeholder), and Messages go natively to `/coding/v1/messages` (`servesMessages`); the Kimi API Platform kinds get the same tool and history normalization but keep `reasoning_effort`. Plan limits come from `GET /usages` (`kimiLimits`: `limits[].detail` with `window.duration`/`timeUnit`, plus the weekly `usage` summary). `muse_code` signs in with the device flow of `auth.meta.com` (public Muse Code client id), then mints an API key at `api.meta.ai/muse-code/key` with the device-client token (`dca:`); the key is stored as `access` with a far-future `expiresAt`, the `dca:` token as `refresh`, and a 401 re-mints it through `renewRejectedLogin`. Models come from `GetCliModelConfigs` grouped by base model, and limits from `GetUserStatus` (daily and weekly percent remaining with reset times). - Sign-in accounts can also be imported from auth files, pasted JSON, or a running CLIProxyAPI (`src/lib/providers/auth-import.ts`, `src/lib/providers/cliproxy-import.ts`; parsing in `src/lib/gateway/upstreams/auth-file-import.ts`). `freshAuthFileSession` never trusts the file's expiry: it renews when due, checks the access token upstream (Codex usage, Claude profile, Google userinfo), refreshes once on 401, and answers `AUTH_FILE_REVOKED` when the token is dead. Devin files carry only a session token (`session_token`, `api_key`, or `token`, also under `metadata`); they are checked with `GetUserStatus` and fail as revoked on 401 or 403. Claude and Codex refresh tokens rotate on every refresh and CLIProxyAPI refreshes every auth it holds, disabled ones included, so an import is a one-time move: the CLIProxyAPI import (management API under `/v0/management`, Bearer key used per request and never stored) downloads the chosen files, imports them, and with `removeFromSource` (on by default in the console) deletes a file at the source only when every account in it was imported; it writes `provider.import_cliproxy` without the key. It connects through `guardedFetch(true)` because CLIProxyAPI usually runs on a private address.
- Add-account links let people without a console login connect their own subscription account. `providers:manage` creates and revokes them in the Subscriptions tab (`src/lib/providers/sub-add-links.ts`, audit `provider_sub_add.create` / `.delete`); creating one needs a fresh second factor (`requireStepUp`, checked after input and targets so a rejected input does not spend the code); the link token and each contributor's manage token are 32 random bytes in base64url, stored only as `sha256` and shown once. A link exists only while it is usable: revoking deletes it, the sign-in that fills its last slot deletes it in the same transaction, and the sweep job `sub_add_links` (`pruneSubAddLinks`, `src/lib/providers/sub-add-prune.ts`) deletes expired or used-up leftovers; each deletion writes `provider_sub_add.delete` with the link state as `before` and `reason` `revoked` | `used_up` | `expired`, and the console lists only usable links. Deleting a link cascades its targets and sets `SubAddAccount.linkId` to null; the account keeps the link label in `SubAddAccount.label`, which the console shows as `ProviderView.sharedVia`. The public pages call `src/lib/providers/sub-add.ts`, which authenticates by token alone, re-checks the link on every step, rate limits per client IP and per link, maps unknown failures to the neutral `SUB_ADD_UNAVAILABLE`, and never returns credentials to the browser. `storeSubAddAccount` (`src/lib/providers/sub-add-store.ts`) adds the account in one serializable transaction that re-reads the link and its `added` count (`withSerializableRetry`, `src/lib/db/serializable.ts`), refuses every path unless the link is `active`, and applies the link's restriction. A new account increments `added` before inserting the connection, so concurrent sign-ins queue on the link row and retry as serialization failures instead of deadlocking against the deletion of a filled link. It matches an existing account like every other sign-in path, but overwrites a match only after the new tokens were checked against the provider (`checkSignInSession`, `src/lib/gateway/upstreams/subscription-limits.ts`, account usage endpoint with the fresh tokens: 2xx or 429 is valid, 401/403 answers `SUB_ADD_LOGIN_INVALID`, anything else `SUB_ADD_LOGIN_UNVERIFIED`); without that check the transaction refuses (`loginVerified`) and the existing connection, its login, and its management stay untouched. A verified renewal moves management to the contributor: it upserts the `SubAddAccount` with their manage hash, keeping `linkId` of an earlier link contributor or using `linkId` null for a console-added connection, so renewing never uses a slot. Removing a connection whose `SubAddAccount.linkId` is set (manage page, console, superseded sweep) decrements that link's `added` inside `removeProviderConnection` (`src/lib/providers/provider-removal.ts`), so a still open link gets the place back; a filled link is already deleted. New accounts write `provider.sub_add_added` with actor `sub-add:<linkId>`. A contributor's manage token lists and disconnects only the accounts it added or took over (`removeProviderConnection`, audit `provider.sub_add_removed`, actor `sub-add` once the link is gone), even after the link was deleted. It does not expire, but the contributor can renew it (`renewSubAddManage`: one update moves every account to a new token, shown once, and the old one stops working) or deactivate it (`revokeSubAddManage`: `manageHash` becomes null and the accounts stay connected), audited per account as `provider_sub_add.manage_renew` / `.manage_revoke` without token values. A null hash matches no token, a token without accounts answers `SUB_ADD_UNAVAILABLE`, and a sign-in that brings a deactivated token gets a fresh one.
- A request moves between sign-in accounts of one kind when an account answers 429, 401, or `no_provider_key` (`withDeployment`, `src/lib/gateway/dispatch/chat.ts`): beyond `num_retries` it may switch once per account in the pool (`accountBudget`) and never retries an account it already tried (`RunRouting.tried`). A 401 first forces one token renewal (`renewRejectedLogin`, `src/lib/gateway/upstreams/credentials.ts`, deduplicated per provider) and retries the same account. A run keeps its account through `prompt_cache_key`: `runSession` hashes it and `readPin` / `writePin` (`src/lib/gateway/routing/account-affinity.ts`, memory plus Redis, `PIN_TTL_MS` six hours) let `acquireGroup` prefer the pinned account before the account strategy; a switch moves the pin. The conversation history is the context the next account receives. On `codex` the account-bound encrypted reasoning is dropped from history when the account changes (`dropAccountReasoning`, `src/lib/gateway/routing/account-handoff.ts`), and an upstream that still rejects foreign reasoning gets one retry without it (`rejectsForeignReasoning`). When every account is parked behind a usage limit (cooldown longer than `COOLDOWN_MS`, from this request or an earlier one, including the overflow group), the router throws `waitingError` and the caller gets 429 `rate_limit_exceeded` (`rate_limit_error` on Anthropic surfaces, never `overloaded_error`) naming the provider and the earliest reset (`limitMessage`, `src/lib/gateway/core.ts`); `gateResponse` adds `retry-after` and sets `x-should-retry: false` past `CLIENT_RETRY_MAX_SECONDS` so Claude Code and the Stainless SDKs stop retrying blindly. Short transient cooldowns stay 503 `no_healthy_deployment` with `retry-after`. When the accounts failed for other reasons, the caller gets the last upstream error instead of `no_healthy_deployment`.
- Account handover: routing loads `enabled` and the login `status` with every route, so a paused, deleted, or signed-out (`expired`) account gets no new request, and a session pinned to it moves on its next request to the account the account strategy picks, preferring the pinned kind (`pinnedKinds`), with `handoffAt` at the current history length. The stale pin is the handover record (Codex reasoning is dropped behind it), so pins are never deleted when an account goes away; they expire after `PIN_TTL_MS`. Every assigned account signed out answers 503 `no_provider_key` (`ERR_SIGNED_OUT`, alerted like `no_healthy`). Open streams finish on the connection and token they started with; a request that acquired a removed account fails over at `deploymentAuth`, whose login read is always fresh. `writePin` is compare-and-set (`SETTLE_PIN_SCRIPT` in Redis, the same rule in memory): it writes when no pin exists or the stored pin still names the account the request read, keeps the larger `handoffAt` for the same account, and otherwise keeps the stored pin, so parallel requests of one session settle on one account. With `REDIS_URL` the Redis pin wins over the local copy, which only serves when Redis fails or has no entry. Reactivation (`reactivateAccount`, `src/lib/gateway/routing/account-reactivation.ts`) runs on resume, a new API key, and every renewal of an existing connection (console sign-in, auth-file and CLIProxyAPI import, add-account link): it clears the account's cooldowns and failure counts (`clearCooldowns`), its cached limits (`forgetLimits`), and the login's refresh backoff (`clearRefreshBackoff`, `retryAt` and `failures` only; never `version`, so an in-flight refresh can still store its rotated tokens). Pins elsewhere stay put; only new sessions and sessions whose account became unusable land on a reactivated account. Account strategy changes reach the gateway within the 5-second policy cache and only affect unpinned sessions. Paused accounts keep refreshing in the sweep, so resuming needs no sign-in. Pause and resume write `provider.pause` / `provider.resume` with `before.enabled`; every pin move logs `gateway.account_handover` (kind, from, to, failover). `acquireGroup`'s release is idempotent, so a stream that ends and is cancelled frees its in-flight slot once.
- Subscription limits are polled server-side into `ProviderLimitSnapshot` (`src/lib/gateway/upstreams/limit-store.ts`, sweep and manual refresh in `src/lib/providers/limit-refresh.ts`), so every tab, replica, and refresh click shares one upstream read per account. `subscription-limits.ts` only parses and fetches (`fetchSubscriptionLimits`, `LimitsFetchError` with `SIGN_IN_EXPIRED`, `UPSTREAM_AUTH`, `UPSTREAM_FAILED`, `UPSTREAM_RATE_LIMITED`) and keeps the per-process copy routing reads (`limitsSnapshot`). Every fetch first claims a row lease (`leaseUntil` / `leaseToken`, 60 s) with an atomic `updateMany` whose conditions also check that the account is still due, so two replicas never read the same account at once and the loser of a manual or forced read waits for the winner's write. The maintenance sweep job `subscription_limits` (before `auto_resets`) polls enabled accounts with an active sign-in, at most 32 per sweep and 4 at a time, and at most 4 Claude usage reads (polls and reset views together) per sweep: every 5 minutes, Claude every 30 minutes (`LIMITS_POLL_MS`, `CLAUDE_POLL_MS`, plus or minus 15% jitter), or 30 to 45 s after the last exhausted plan window resets when that comes sooner, never sooner than 60 s (Claude skips that recheck while traffic headers are recent); paused and expired accounts are not polled. Claude responses on every gateway path (`observeUpstreamLimits` in `proxyJson`, `proxyRaw`, and `openUpstreamStream`) carry `anthropic-ratelimit-unified-*` headers: `observeClaudeLimits` parses the five-hour and weekly windows (`claudeHeaderWindows` in `observed-limits.ts`; utilization is a fraction, unknown or odd values are ignored), merges them into the per-process copy at once and into the snapshot without blocking the request (model windows, extra usage, and plan stay from the last full read; `limits.observedAt` records the headers; `fetchedAt` stays the full read), writing at most every 30 s per account and process unless a window flips to reached, only when a window moved by a point or its reset moved, and at least every 5 minutes while traffic flows. A header write pushes `nextAt` to 30 minutes after the traffic, at most 2 hours after the last full read (`CLAUDE_TRAFFIC_POLL_MS`). Failures back off on `nextAt` (1 minute doubling to 30 minutes; sign-in errors start at 5 minutes; a renewed login version makes a failed account due at once), and consecutive 429s store a `retryAt` of 15, 30, 60, then 120 minutes, or the Retry-After when longer (`rateLimitWait`, up to 10% jitter on `nextAt`), that blocks every refresh, manual ones included; a successful read resets the streak. The Claude reset view shares that block: its 429 writes the same `retryAt` (`blockUsageReads`) and it never reads while one holds. A failed read keeps the last limits and sets `error`. Manual refresh (`loadProviderLimits({ refresh: true })`, `loadSubscriptionLimits({ refresh: true })` for enabled accounts) goes through the same lease at most once a minute per account, Claude every 5 minutes (`manualRefreshGap`), and returns the snapshot; both actions keep their signatures and return `LimitSnapshot` items (`{ id, limits, error, version, checkedAt, nextAt, retryAt }`, `version` grows with every write) plus `at`. Routing hydrates its per-process copy from the snapshots at most every 15 s (`hydrateLimits`) and never calls a provider; a gateway 429 only pulls the account's next poll forward (`nudgeLimits`), and not when its response carried unified headers. Reset paths read through the lease with a maximum age that counts traffic headers (`freshLimits`, `limitsUpdatedAt`: 10 s before a claim, 0 right after a reset, 10 minutes for automatic decisions and 60 s for the 429 hook, Claude 60 and 5 minutes). Banked-reset details are stored with the snapshot (`resets`, `resetsAt`) by `refreshResetView` under the per-account reset lock, at most every 15 minutes for Codex and every hour for Claude (2 and 5 minutes on manual refresh); a failed Claude read keeps the old view and retries after its backoff, a redeem expires the view, and reset state changes bump the snapshot `version`. Reads compose the view with the current pending claim (`resetCreditsView`, `src/lib/gateway/upstreams/reset-state.ts`). Every snapshot write calls `notifyLive("limits")`, and so do provider removal (`removeProviderConnection`) and a refresh that marks a login `expired`, so the feed drops those accounts at once. `forgetLimits(providerId)` (`subscription-limits.ts`) is the public invalidation hook for an account that becomes usable again (resumed, signed in again, renewed, reset redeemed): it drops the per-process copy and, in the snapshot, clears `error`, `failures`, and `fetchedAt` and sets `nextAt` to now, so the next sweep polls it; the kept limits stay visible in the console, but `hydrateLimits` and `freshLimits` ignore a snapshot without `fetchedAt`, so no replica routes on them. A provider's Retry-After (`retryAt`) survives `forgetLimits`. The add-account sign-in probe `checkSignInSession` checks fresh tokens with a direct usage call on purpose and never reads or writes snapshots.
- Banked usage resets live in `src/lib/gateway/upstreams/reset-credits.ts` (upstream contracts, parsing, grant choice) and `reset-redeem.ts` (claims, sweep, hook), with the console service in `src/lib/providers/resets.ts`. Codex reads and spends `wham/rate-limit-reset-credits`; Claude reads `cedar_ember` grants from `/api/oauth/usage?cedar_ember=1&skip_spend=1` and spends them through `reset_rate_limits`. Claude rate-limits that read, so the console reads it at most hourly (five minutes on manual refresh), automatic decisions at most every ten minutes, and a 429 backs off for its Retry-After (an hour without one). A redeem holds a per-account lease and saves the pending claim (`Setting` `provider_reset:<id>`) before the request goes out; an unknown outcome is retried only with the same request id within `RETRY_WINDOW_MS` (ten minutes) and is otherwise closed as `expired` by the next fresh limits read, never claimed twice. Automatic resets (`AccountRouting.autoReset`, `autoResetPercent`, `autoResetScope` `pool` or `account`; `src/lib/gateway/routing/auto-reset-policy.ts`) run in the maintenance sweep (`auto_resets` job) and from `autoRedeemIfDue`, which the gateway fires without awaiting on a 429; they never run while a claim is unresolved, at most once per account per `AUTO_GUARD_MS` (15 minutes), and in pool scope once per kind per 15 minutes on the account that would wait longest. A successful reset re-reads the limits and clears the account's cooldowns (`clearCooldowns`, `src/lib/gateway/routing/provider-health.ts`, which leaves a Redis marker so other replicas drop their local cooldown). Redeems write `provider.reset_redeem` (actor user id or `worker`, no tokens) and policy saves `account_routing.auto_reset`.
- Account routing is per provider kind: `AccountRouting` holds one `AccountStrategy` per sign-in kind (`smart` when unset; `inherit` keeps the alias strategy) and `acquireGroup` applies it to the accounts of that kind before the alias strategy picks (`byAccountPolicy` in `src/lib/gateway/routing/runtime.ts`). Accounts can be restricted: `ProviderConnection.restricted` plus `ProviderAssignment` rows (company, department, project, person, or key) decide which callers may use an account (`accountAllowed` in `src/lib/gateway/routing/account-access.ts`); the principal's access is passed through `withDeployment` and an alias whose accounts all exclude the caller answers 403 `account_not_assigned`. A paused provider is skipped, and when every deployment is paused the router answers 503 `no_healthy_deployment` without an exhaustion alert.
- Routes form three pools (`routePool`, `src/lib/gateway/routing/route-pool.ts`): deployments of sign-in kinds are the `subscription` pool, deployments of a provider with `ProviderConnection.internal` the `internal` pool, all others the `api` pool. `internal` is a required field of the provider shape `routePool` reads (`PooledRoute`), so a select that drops it does not compile; sign-in kinds refuse the flag (`INTERNAL_SIGN_IN`). HTTP surfaces only carry a `PublicPool`: the route factories pass theirs to `gateRequest` (`principal.pool`), and `withDeployment` and `forwardToModel` take `pool` (default `api`) and filter routes, fallbacks, overflow, and `auto` with `routable` (the `internal` pool also uses API routes, never a subscription), so `/api/v1`, batches, and the playground never reach a subscription or an internal provider and `/api/subscription/v1` never reaches an API key. An alias whose routes all sit in the other public pool answers 404 `model_not_found`; one whose routes are all internal answers on public surfaces exactly like an unknown alias (`hiddenFrom`), is never listed (`listedIn`), never matches a model template (`loadModelPolicies` drops internal routes), and is left out of the playground, API reference, and MCP builder lists; catalog auto-routing skips internal providers.
- Cost bills 5-minute cache writes at 1.25x and 1-hour cache writes at 2x the deployment input rate; cache reads at 0.1x except Claude Fable/Mythos 5.1 (0.025x) and Claude Opus 5.5 (0.05x) (`src/lib/gateway/billing/cost.ts`).

## Architecture

- `src/lib/auth/` session, cookies, guards, OIDC and JWKS, SCIM, throttle.
- `src/lib/gateway/` the `/api/v1` runtime, one folder per concern: `access/` (gate, principals, key restrictions, model access), `endpoints/` (route factories, batches, videos, media), `protocols/` (request parsing, Responses and its stream encoder, legacy Completions, Messages, Anthropic, chat stream piping, and SSE conversion), `dispatch/` (upstream calls, service modes), `routing/` (strategies, accounts, health, pools), `upstreams/` (provider kinds, subscription sign-in and credentials, discovery, provider prices), `catalog/` (model catalog sync and aliases), `billing/` (budgets, cost, metering, price schedules, markups), `request-logs/`, `safety/` (guardrails, PII), `cache/`, and `storage/` (stored objects and files). `core.ts`, `errors.ts`, and `api-paths.ts` stay at the root. A new gateway module goes into the folder of its concern, never the root.
- `src/lib/alerts/` alert webhooks, rules, events, and formats. `src/lib/settings/` enterprise settings. `src/lib/usage/` usage statistics, totals, and forecast. `src/lib/export/` CSV, PDF, and Markdown exports. `src/lib/audit.ts` audit rows.
- `src/lib/keys/` key views and key management. `src/lib/tenancy/` companies, departments, projects, people, and budgets. `src/lib/reports/` usage report schedules and delivery. `src/lib/models/` model groups, templates, and enabled aliases. `src/lib/providers/` provider connections and subscription account routing. `src/lib/pricing/` markups.
- `src/lib/management/` management-key auth, scope, `/api/mgmt` route wrapper, serializers, Structure helpers.
- `src/lib/mcp/` MCP server client, SSRF guard, assignment resolution, gateway tool loop, and the console service.
- `src/lib/updates/` build version, release update check, the updater bridge (`updater.ts`, signed by `updater-signature.ts`, state in `updater-store.ts`), and the console live stream (`live.ts`, `live-stream.ts`).
- `src/lib/bootstrap/` catalog and boot.
- `src/lib/` must not import route modules; the ESLint layering rule enforces it.

## Prohibited patterns

- Do not call `revalidatePath` / `revalidateTag` / `router.refresh`.
- Do not log passwords, SCIM tokens, or raw API keys.
- Do not create the first operator from register, SSO, or SCIM.
- Subscription sign-in (Claude, Grok, Codex, Antigravity, Kimi Code, Muse Code, Devin) and the client identities it needs are an owner decision that accepts the vendors' terms risk: accounts can be limited or banned.
