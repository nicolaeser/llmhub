# Security and privacy

Load before changing sign-in, sessions, account security, roles, permissions, first-operator setup, virtual keys, PII, or environment secrets.

## Mandatory rules

- One secret, `APP_SECRET` (at least 32 characters). `src/lib/crypto.ts` derives HKDF-SHA256 subkeys: `signingSecret()` signs session cookies, OIDC state, and try-bearers; the `data` subkey seals TOTP secrets, provider keys, and secret settings and keys recovery-code HMACs; `updaterKey()` signs both directions between the app and the updater container.
- The Docker socket is root on the host. Only the updater container in `docker-compose.au.yml` mounts it, with no ports and only `APP_SECRET` from `.env` (see [operations.md](operations.md)). `POST /internal-api/updater` trusts nothing but a valid signature, and the updater trusts only signed replies. Starting an update or changing `auto_update` needs `settings:manage` and writes `updater.command` / `settings.auto_update` audit rows.
- Sessions are opaque 256-bit tokens. The cookie is `token.hmac` (`src/lib/auth/cookie.ts`, HMAC with `signingSecret()`); the database stores only `sha256(token)` (`Session.tokenHash`). `src/proxy.ts` only checks the signature; `getSession` checks the row, 7-day idle and 30-day absolute expiry, a blocked user, and a completed second factor. Starting a session revokes the session the browser already held (`setSessionCookie`, `startSession`, SSO callback). Every SSO session has an `SsoSession` row (issuer, subject, the provider's `sid`, and, while roles come from the provider and discovery lists `offline_access`, the sealed refresh token) so that access removed at the identity provider ends the session within minutes (`src/lib/auth/sso-sessions.ts`): `POST /sso/backchannel-logout` ends the sessions named by a verified logout token (by `sid`, else every SSO session of that subject), and the maintenance sweep refreshes each stored grant once every 5 minutes (`SSO_REVALIDATE_INTERVAL_MS`). A refused refresh, a different subject, or, while roles come from the provider, no known app role ends all of that person's sessions and clears their role (`role.changed`, `user.role_synced` with `roleId: null`); a changed app role is re-applied, and `getSession` reads the role on every request, so a demotion holds from the next request. A rate limit, outage, or network error keeps the session and checks again after the interval.
- Every session records its factor (`TOTP` | `RECOVERY` | `PASSKEY` | `SSO`). A session without a factor must be rejected.
- Two-factor authentication is mandatory for password sign-ins. `passwordSignIn` never creates a session; it issues a `LoginChallenge` (`VERIFY`, `ENROLL`, or `PASSWORD`) in a separate `SameSite=strict` cookie (`src/lib/auth/sign-in.ts`, `src/lib/auth/login-challenge.ts`). Setup and public registration issue an `ENROLL` challenge instead of a session. OIDC sign-ins count as the `SSO` factor.
- TOTP secrets are sealed with AES-256-GCM bound to the user id (`src/lib/auth/totp.ts`, `src/lib/crypto.ts` data subkey). Accepted codes advance `lastTimeStep` with a conditional write; recovery codes are keyed HMACs consumed with a conditional `usedAt` write; passkey counters advance with a conditional write.
- Every second-factor check (TOTP, recovery code, passkey, step-up, enrollment confirm) runs through `guardSecondFactor` (`src/lib/auth/second-factor.ts`): it reserves a `LoginAttempt` row before verifying, so parallel guesses cannot pass the lockout (10 per 15 minutes, 30 per 24 hours per user). A failure keeps the row; success clears the user's failures; unrelated errors release the reservation. Reaching the limit ends pending sign-ins and records `2fa.locked`.
- Password sign-in reserves attempts before hashing: 10 failures per account and client and 50 per account per 15 minutes (`reserveAttempts`), plus 30 sign-ins per client per minute. Passwordless passkey sign-in is limited to 20 per client and 120 overall per minute before a ceremony row is stored. Window limits use Redis when configured and a bounded in-memory map otherwise (`src/lib/rate-limit/window.ts`). Client keys come from `clientBucket(clientIp(...))` and are only as trustworthy as `IP_MODE` matches the deployment, so account-wide limits must stay in place.
- Client addresses come only from `clientIp` in `src/lib/http/client-ip.ts`, chosen by `IP_MODE`: `proxy` (default) trusts only the last `X-Forwarded-For` entry, the one the reverse proxy appends, and never falls back to earlier, client-supplied entries; `cloudflare` trusts only `CF-Connecting-IP` (`CF-Connecting-IPv6` when Cloudflare sends a pseudo IPv4 address from 240.0.0.0/4); `direct` trusts no header and reads the socket peer, which `configureClientIp` (from `src/instrumentation.ts`) copies into a random per-process `x-llmhub-peer-*` request header on the `http.server.request.start` diagnostics channel, because Next.js keeps a client-sent `X-Forwarded-For` and fills it from the socket only when it is missing; requests accepted before `register()` subscribed carry no stamp and resolve to `null`. Addresses are canonical (no port, brackets, or zone id; IPv6 compressed lowercase; IPv4-mapped IPv6 as IPv4); anything else is `null` and logged as `client_ip.unresolved` at most once a minute. No other module may read forwarding headers or `remoteAddress` (`src/tests/client-ip.test.ts`). Key IP allowlists compare canonical addresses (`ipAllowed`); throttle keys use `clientBucket` (IPv6 per /64, `unknown` when unresolved); sessions, security events, and management-key principals store the full address.
- Replacing the authenticator, regenerating recovery codes, adding or removing a passkey, setting another user's password, and resetting another user's two-factor require a step-up code (`requireStepUp`). Password and authenticator changes sign out every other session.
- One password policy (`src/lib/auth/password-policy.ts`) backs `newPasswordSchema` and every password write: 10 to 256 characters with a letter and a number (`WEAK_PASSWORD`), not a common, sequential, or repetitive password, and not containing the username or email name (`PASSWORD_GUESSABLE`). `parseAuthInput` and `inputErrorCode` surface these codes instead of `VALIDATION`.
- Passkeys use `@simplewebauthn` with the relying party from `NEXT_PUBLIC_APP_URL`; they are only offered for HTTPS domains or `localhost`. WebAuthn challenges live in `AuthCeremony` and are consumed once.
- Permissions come from the catalog in `src/lib/auth/permissions.ts` (domain plus `view` / `work` / `sensitive` level). Code checks permissions, never role names; `requirePermission` throws `AuthError("FORBIDDEN")`. A console user with `User.orgId` is company-scoped: `effectivePermissions` keeps only `COMPANY_PERMISSIONS`, and `companyOf`, `inCompany`, `keyScope`, and `spendScope` (`src/lib/auth/scope.ts`) must limit keys, tenancy, budgets, usage, logs, and exports to that company; company and console-user budgets and company create, rename, or delete answer `PLATFORM_ONLY`. The owner is never company-scoped by role, but the owner's company view (`workspaceOrgId`) is company scope for every check above. Global state is platform-only through `assertPlatform` / `requirePlatformPermission` (`src/lib/auth/scope.ts`, `src/lib/auth/guards.ts`): the global PII and guardrail policies, markups and model templates (load, save, delete), every read and save on the Settings page (the updater switch and commands stay available from the top bar), every provider, subscription account, add-account link, model group, and catalog service (reads included), budget alert thresholds, MCP server management (`requireMcpManager`), and console users and roles; in the company scope, guardrail overrides list and edit only that company's organization, departments, projects, and keys. `/settings`, `/users`, `/providers`, and `/models` also redirect the company scope server-side (`requirePlatformScope` in their `layout.tsx`); hiding navigation is never the only guard. Roles are editable permission bundles; `admin`, `operator`, `finance`, and `viewer` are templates seeded once and restorable.
- The setup user is the owner (`User.isOwner`): every permission, cannot be blocked, deleted, or re-roled. Nobody grants or manages beyond their own permissions (`src/lib/auth/grants.ts`); role and user edits use a `revision` fence.
- Management keys (`ManagementKey`, `src/lib/management/auth.ts`) are personal `/api/mgmt` credentials: created on the account page with a step-up code and `assertCanGrant`, limited to `MANAGEMENT_PERMISSIONS` (no users, roles, settings, or tools), stored as `sha256` with an 8-character prefix, shown once, at most 25 per user, optional expiry. At request time the scope is intersected with the owner's current role; blocked owners and expired keys fail with `INVALID_API_KEY`. Create and revoke write `management_key.*` security events and the audit log.
- Credentials for imports are used once and never stored: the CLIProxyAPI management key travels with each request of the import and is not saved, audited, or logged; imported subscription tokens are sealed in `ProviderLogin` like signed-in ones. Five wrong management keys lock the caller's IP at CLIProxyAPI for 30 minutes, so its `401` (`CLIPROXY_KEY_REJECTED`) and ban (`CLIPROXY_LOCKED`) answers must not be retried automatically.
- A saved Google OAuth client secret for Antigravity sign-in is sealed in `Enterprise.antigravity` (`src/lib/settings/enterprise.ts`), set through `saveAntigravityConfigAction` (needs `providers:manage`), and written to the audit log without its value; neither it nor the image's bundled secret (`antigravity-client-secret`) is ever returned to the browser, which only learns whether each exists.
- Security-relevant changes write `UserSecurityEvent` rows; console mutations also write the gateway audit log. Security events carry IP addresses and are deleted after `Enterprise.security_retention_days` (default 90, enough for incident review; 0 keeps them).
- First operator: `/internal-api/setup` (`createFirstAdmin` in `src/lib/bootstrap/first-admin.ts`, called by the setup page action). The layout redirects home when `prisma.user.count() > 0`; the service recounts inside a serializable transaction. Login, register, and `/sso/login` must not redirect to setup, and `/sso/login` must not read the user count; no message may name the setup path: the root layout sends every namespace to every page, so such a string would reach crawlers on the login page.
- Public registration, invites, SSO upsert, and SCIM create must not insert the first user; while the user table is empty they answer `SETUP_REQUIRED`, except the SSO callback, which sends the generic `?sso=error` so a visitor cannot tell an empty instance from a failed sign-in.
- OIDC uses the authorization code flow with PKCE (`S256`), a random `state` distinct from the `nonce`, and a signed, 10-minute state cookie that carries the nonce, the code verifier, and the purpose (`sign_in` or `role_check`) (`src/lib/auth/oidc.ts`).
- OIDC sign-in (`src/lib/auth/oidc.ts`, `src/lib/auth/sso-user.ts`): discovery must name the configured issuer (trailing slashes and a pasted `/.well-known/openid-configuration` are dropped), except that a Microsoft Entra tenant-domain issuer (`https://login.microsoftonline.com/<domain>/v2.0`) accepts the tenant-ID issuer of the same host, which then verifies ID tokens and keys `UserIdentity`; multi-tenant templates (`{tenantid}`) are refused; the token request uses `client_secret_basic` when the provider lists it before `client_secret_post` (else post); ID tokens verify against the JWKS key with the header `kid` (refetched once for rotation) with RS/PS 256–512, ES256/384/512, or EdDSA, never `none` or HMAC (`src/lib/auth/jwks.ts`). Accounts match by `UserIdentity` (`issuer` + `sub`, unique, one per user and issuer), then by `User.externalId` equal to `sub` or Entra `oid` (SCIM-provisioned), then by verified email (`email_verified` or Entra `xms_edov`); the first match is linked. A second subject of the same issuer, the owner, a missing email, or an email outside `Enterprise.oidc.allowed_domains` is refused. New accounts get the role below and `default_org_id`.
- SSO and SCIM roles resolve in `directoryRoleId` (`src/lib/auth/directory-roles.ts`): group rules (`Enterprise.oidc.role_mappings`, first match by group value, case-insensitive), then provider app roles, then `default_role_id`, then `viewer`. Rule values come from the `groups_claim` (exact key or dotted path), the SCIM groups the user belongs to (display name or external ID), and, in app-roles mode, the `app_roles` values. While rules exist every sign-in and SCIM membership change re-applies them (`role.changed` security event, `user.role_synced` audit); the owner is never changed. Saving rules needs `settings:manage` and the right to grant every mapped role.
- Provider app roles are the `app_roles` scope and claim, advertised in discovery `scopes_supported`. `/sso/login` adds the scope only while discovery lists it and drops a hand-typed `app_roles` otherwise. Whether roles come from the provider is the stored switch `Enterprise.oidc.app_roles` ("Roles come from {provider}", off by default); discovery and the token never switch it. Saving sign-in settings turns it on only for a first configuration (no `UserIdentity` for that issuer yet, the role fields untouched, discovery lists `app_roles`). Every existing configuration keeps it off until an admin turns it on with `setAppRolesMode`, which needs `settings:manage` and a check sign-in from the last 15 minutes by that admin whose `app_roles` contains `admin` (`src/lib/auth/app-roles-check.ts`). The check uses the same state cookie with the signed purpose `role_check`; the callback branches only on that verified purpose, requires the settings manager's session before exchanging the code, and never creates a session or touches users. Turning it off needs no check.
- While the switch is off, app roles change nothing. While it is on, the `app_roles` array maps `admin`, `operator`, `finance`, and `viewer` to the role template of the same key (highest wins, unknown values ignored), every sign-in re-applies the role, and a person with no known role and no `default_role_id` is refused with `?sso=no_role` and their sessions are revoked; a missing claim counts as no role. The identity row records it (`UserIdentity.appRoles`): such people show "Managed by {provider}" on the console users page, `assignUserAccess` refuses a role change with `ROLE_MANAGED`, and SCIM group changes skip them. `{provider}` is `Enterprise.oidc.display_name`, else the issuer host.
- `Enterprise.oidc.sso_only` (effective only while OIDC is ready) rejects password and passwordless passkey sign-in for non-owners with `SSO_REQUIRED` and disables self-registration; the owner keeps password plus second factor as break-glass.
- Cookie-authenticated `POST` routes under `/internal-api/account` reject cross-site requests with `FORBIDDEN` (`isSameOriginRequest`, `src/lib/auth/request-origin.ts`). `/internal-api/account/expired` clears the cookie only when the session is invalid; logout also drops the pending login challenge and passkey ceremony.
- Self-registration is off by default (`Enterprise.registration_enabled`, Settings → General). When on, accounts get the `viewer` template and must enroll two-factor. The owner always signs in with password and second factor, independent of OIDC; SSO creates accounts on first sign-in regardless of the switch.
- Password reset needs `SMTP_URL`. Requests are limited to 10 per IP and 3 per email per hour (`consumeQuota`), answer the same whether the account exists, send mail in `after()`, keep one live token per user, and every successful reset deletes the user's tokens and sessions.
- Throttle rows in `LoginAttempt` are kept for 24 hours (`ATTEMPT_RETENTION_MS`) so the 24-hour second-factor window holds. The maintenance sweep also runs `purgeAuthRecords` (`src/lib/auth/cleanup.ts`): idle or expired sessions, expired or consumed login challenges, expired WebAuthn ceremonies, and abandoned authenticator enrollments.
- Return paths after login must stay in-app (`src/lib/auth/return-path.ts`).
- CSV exports go through `toCsv` (`src/lib/export/csv.ts`), which prefixes string cells starting with `=`, `+`, `-`, `@`, tab, or carriage return with `'`, because client-controlled values such as tags and labels reach finance spreadsheets. Must not hand-build CSV.
- Label allowlists are edited with `settings:manage` for the platform (`Enterprise.label_keys`, Settings → Logging & alerts, audit `settings.request_labels`) and `tenancy:manage` for a company (`Organization.labelKeys`, company page, audit `org.label_keys`); only allowlisted keys are ever stored.
- Request content (prompts and responses) is logged by default and, like request log metadata, kept 30 days unless an admin sets `content_retention_days` / `log_retention_days` (0 keeps it). It is off when `Enterprise.log_content` is false, when the key has `VirtualKey.logContent` false, or when the request's user has `User.logContent` false; the user switch also covers keys that user owns. `contentSkip` records the reason. Only `users:manage` changes a user's switch, and the owner is not manageable.
- Reading stored content requires `logs:content` (sensitive; only the `admin` template). Log rows stay scoped by `spend:read` / `spend:read-all`. Every detail view that returns content writes a `log.content_view` audit row.
- PII policy (`Enterprise.pii`) and content guardrails (`Enterprise.guardrails`: denylist and regex rules, prompt injection heuristics, output secret checks) are global; a company, department, project, or key overrides single parts (`pii`, `injection`, `secrets`, `rules`) through a `PolicyOverride` row. Each part comes from the most specific level that sets it (key, then project, then department, then company), else the global policy. Overrides are edited on the Guardrails page with `settings:manage` and audited as `policy.override`. Request handling and logging must use the effective policies from `resolvePolicies(principal)`, which reads the whole chain in one query; the console computes the same result with `effectivePolicies` (`src/lib/gateway/safety/policy-layers.ts`).
- While the effective PII policy is enabled, stored request and response content, the logged error, the logged tag, and request label values (log and `UsageLabelDaily`) are masked with it, even when output redaction to the client is off. Each log records `piiMode`, `piiInput`, and `piiOutput`, and in restore mode `piiRestore`: the placeholder tokens sent to the model and the ones the reply used in text and in tool input, never the original values, which are neither stored nor sent to the browser; requests stopped by block mode are logged with outcome `pii_blocked`. Guardrail matches are logged in `guardInput` / `guardOutput`, and guardrail blocks with outcome `guardrail_blocked`. Request content logging is the product's audit store, not application logging.
- PII catalog matches Presidio-style ids in `src/lib/gateway/safety/pii.ts`. `IP_ADDRESS` (default on) covers public addresses only; `PRIVATE_IP_ADDRESS` (default off) covers internal ones: 10/8, 172.16/12, 192.168/16, 127/8, 169.254/16, 100.64/10, 0.0.0.0, `::1`, `::`, fe80::/10, fc00::/7, and IPv4-mapped forms of the IPv4 ranges. The documentation ranges (192.0.2/24, 198.51.100/24, 203.0.113/24, 2001:db8::/32) count as public, because they stand in for public addresses in examples and tests. Saved entity lists are not migrated: a list without `PRIVATE_IP_ADDRESS` lets internal addresses through, which is the intended default.
- Every PII policy (global and override) has a `detector` (`patterns`, the default for stored and new policies, `model`, or `both`) and a `failure` (`patterns` or `block`). Credential entities (`CREDENTIAL_ENTITIES`: `SECRET`, `JWT`, `PRIVATE_KEY`, `CONNECTION_STRING`, `ENV_SECRET`) always run as patterns first, so secrets never reach the redaction model; `model` adds model spans on top, `both` merges model spans with the non-credential pattern spans (`piiPatternSpans`), and overlapping spans become one (`mergePiiSpans`: union of the extents, label of a credential span, else the longest, else a pattern, else the higher score). Model spans go through the request's vault like pattern matches, so numbering, restore, `piiInput`, and placeholder chips are shared. Model labels map in `MODEL_LABELS` (`src/lib/gateway/safety/pii-spans.ts`): `private_person` → `PERSON`, `private_email` → `EMAIL_ADDRESS`, `private_phone` → `PHONE_NUMBER`, `private_address` → `ADDRESS`, `private_url` → `URL`, `private_date` → `DATE_TIME`, `account_number` → `ACCOUNT_NUMBER`, `secret` → `SECRET` (un-numbered, never restored), `other_pii` → `OTHER_PII`; catalog ids pass through and other labels are dropped. `PERSON`, `ADDRESS`, `ACCOUNT_NUMBER` (default on) and `OTHER_PII` (default off) are `modelOnly` catalog entries without pattern rules. Only enabled entities are kept. A failed, slow, or missing model falls back to patterns with one `pii.detector_failed` warning per model and code a minute (model, code, status; never text or spans), or with `failure: "block"` rejects with `503 pii_detector_unavailable`, logged as outcome `pii_blocked` with pattern-masked content. Detector calls run as `systemPrincipal("pii")`, so their request logs never store content. Output redaction and log masking of responses stay pattern-based. Do not log raw passwords, codes, recovery codes, reset tokens or links, SCIM tokens, plaintext virtual keys, or email addresses; log user ids. Mail and SMTP failures log an error code or name, never the message.
- Error reporting must not carry secrets or personal data. Sentry runs with `SENTRY_DATA_COLLECTION` (`src/lib/sentry/options.ts`): no users, cookies, request or response bodies, URL query values, credential, cookie, or client address headers (the deny list plus Sentry's built-in `auth`, `key`, `token`, `session` snippets cover `authorization`, `x-api-key`, `x-goog-api-key`, `api-key`, and the `x-llmhub-peer-*` header), database or queue payloads, AI inputs and outputs, or stack-frame variables. Sentry attaches `request.url`, the browser location, `Referer`, navigation breadcrumbs, and Next.js `request_path` without that gate, so `scrubEvent` (`src/lib/sentry/scrub.ts`, the `beforeSend` and `beforeSendSpan` hooks) replaces add-account link tokens and every URL parameter value with `[Filtered]` in every event and span string except stack traces and the unsent `sdkProcessingMetadata` (it holds live scopes) and caps exception messages with `errorSummary` (first line, 300 characters, as in logs). Outgoing requests are never recorded and get no trace headers (see [operations.md](operations.md)). Must not set `sendDefaultPii`, enable Replay or Feedback, or pass job data beyond `WORKER_JOB_ID_TAGS`. The CSP `connect-src` in `src/proxy.ts` adds only the ingest origin of the build-time `NEXT_PUBLIC_SENTRY_DSN` (`sentryIngestOrigin`).
