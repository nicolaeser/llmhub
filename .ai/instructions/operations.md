# Operations

Load before changing `Dockerfile`, `docker-compose.yml`, `docker-compose.dev.yml`, `docker-compose.au.yml`, `docker-compose.rm.yml`, `scripts/updater.mjs`, `scripts/updater/`, `scripts/redactor.mjs`, `scripts/redactor/`, `scripts/migrate-deploy.mjs`, `generate-env.sh`, `src/schemas/env.ts`, `src/instrumentation.ts`, `.github/`, or health endpoints.

## Mandatory rules

- Keep the environment minimal. `src/schemas/env.ts` is the only list: `NODE_ENV` (only `production` or `development`; any other value fails the start), `DATABASE_URL`, and `APP_SECRET` (min 32) are required; `NEXT_PUBLIC_APP_URL` defaults to `http://localhost:3000`; `S3_ACCESS_KEY_ID`, `S3_SECRET_ACCESS_KEY`, `SMTP_URL`, `SMTP_FROM`, `OIDC_CLIENT_SECRET`, `REDIS_URL` (trimmed), `BUILD_ID`, and `LLMHUB_REDACTOR_URL` (an http or https URL) are optional; `IP_MODE` is `proxy` (default), `cloudflare`, or `direct`, and any other value fails the start. Read env through `env` from `src/lib/env.ts`, never `process.env.X` (except `NODE_ENV`, `NEXT_RUNTIME`, `NEXT_PHASE`); `redisUrl()` (`src/lib/jobs/connection.ts`) reads `env.REDIS_URL` and parses an explicit source with `envSchema.pick`. Must not add env vars for values that can be hardcoded or saved in Settings. A new variable also goes into `.env.example` (the local development template) and the README configuration table.
- Compose files hardcode the Postgres and Redis images (`postgres:18-alpine`, `redis:8-alpine`) and their ports; only the app image tag, the host port, and the memory caps take defaults (`LLMHUB_TAG`, `LLMHUB_PORT`, `LLMHUB_MEMORY_LIMIT`, `POSTGRES_MEMORY_LIMIT`, `REDIS_MEMORY_LIMIT`). Data lives in bind mounts next to the compose file: `./postgres-data` at `/var/lib/postgresql`, `./redis-data` at `/data` (production Redis adds `--appendonly yes`), and `./rustfs-data` for dev RustFS. `postgres-data` and `redis-data` must stay in `.gitignore`, `.dockerignore`, and ESLint `globalIgnores`; must not switch back to named volumes (`src/tests/docker.test.ts`). Database user, database name, and credentials come only from the generated `.env`: `${POSTGRES_USER}`, `${POSTGRES_DB}`, `${POSTGRES_PASSWORD}`, and `${REDIS_PASSWORD}` in both files (Redis runs with `--requirepass` and `REDISCLI_AUTH` for its healthcheck), `${S3_ACCESS_KEY_ID}` / `${S3_SECRET_ACCESS_KEY}` for dev RustFS, without `:?` or defaults. The app service also loads `.env` through `env_file`; compose overrides `DATABASE_URL` and `REDIS_URL` with in-network hosts built from those values.
- `docker-compose.yml` runs `ghcr.io/nicolaeser/llmhub:${LLMHUB_TAG:-latest}` with `NODE_ENV: production` on `127.0.0.1:${LLMHUB_PORT:-3000}` behind a reverse proxy (Caddy) with Postgres and Redis on the internal network; only `LLMHUB_TAG`, `LLMHUB_PORT`, the `POSTGRES_*` values, `REDIS_PASSWORD`, and the `*_MEMORY_LIMIT` caps are interpolated, the app reads `.env` through `env_file`. Both production files (`docker-compose.yml`, `docker-compose.au.yml`) give the app `stop_grace_period: 330s`, longer than the 300 s `maxDuration` of the gateway routes, so `SIGTERM` lets open requests and streams finish instead of being killed after Docker's 10 s default; every service uses the `x-logging` anchor (`json-file`, `max-size` 10m, `max-file` 5, set explicitly because options alone would apply to whatever driver the daemon defaults to) and a `mem_limit`: app `${LLMHUB_MEMORY_LIMIT:-4g}`, Postgres `${POSTGRES_MEMORY_LIMIT:-2g}`, Redis `${REDIS_MEMORY_LIMIT:-1g}`, updater `256m`. `src/tests/docker.test.ts` checks that the grace period exceeds every route's `maxDuration` and equals the updater's default. `docker-compose.dev.yml` builds `.` as `llmhub:dev` and publishes Postgres `127.0.0.1:5433`, Redis `127.0.0.1:6379`, RustFS `127.0.0.1:9000` / `9001`, app `127.0.0.1:3000`.
- `docker-compose.au.yml` is `docker-compose.yml` plus the auto-updater, never an override file: its `app`, `postgres`, and `redis` services must stay identical to `docker-compose.yml` except that `app` gains the label `llmhub.updater.target=true` (`src/tests/docker.test.ts` compares the files). The `updater` service runs the same image with `node updater.mjs` on the default compose network and gets only the Docker socket, `APP_SECRET` interpolated from `.env` (never `env_file`), and `user: "0:0"` because the host socket belongs to root and the image's `node` user cannot open it; registry lookups and pulls go through the Docker daemon. The `updater` service keeps `pull_policy: always`: Compose only pulls missing images, so a host with an older cached image of the tag (from before the updater existed) would start the updater from an image without `updater.mjs`; pulling for the updater also moves the shared tag, so `up` recreates the app on the same image. The file stays plain otherwise: no extra networks, `cap_drop`, or `security_opt`. It publishes no ports. It is the only compose file that mounts the Docker socket; the app must never get it, because the app handles outside traffic.
- The updater (`scripts/updater.mjs`, `scripts/updater/*.mjs`, Node built-ins only) syncs with the app every 10 s over `POST /internal-api/updater`, checks the registry digest every 5 minutes, and on request or with `Enterprise.auto_update` (default off; automatic installs only while the updater reported within the last 5 minutes) pulls, recreates every running container of its own compose project labelled `llmhub.updater.target=true` with the same config, networks, and aliases (it stops the old container with its `StopTimeout`, 330 s when unset, and writes that value into the new container) (Compose's image label follows the platform manifest digest so `docker compose up` sees no drift), waits up to 10 minutes for healthy, and rolls back on failure; a failed digest is not installed automatically again. Pinned tags (release, `sha-…`, `dev-…`, 40-hex, digests) are reported as pinned. After an app update it replaces its own container; the successor reads the predecessor's state through the Docker archive API (`LLMHUB_UPDATER_PREDECESSOR`), and a leftover `<name>-llmhub-old` container from an interrupted update is restored at start. State and heartbeat live in `~/.llmhub-updater/` (mode 0700), not in the temp directory; the compose healthcheck runs `node updater.mjs --healthcheck`. `LLMHUB_UPDATER_APP_URL` and `LLMHUB_UPDATER_PROJECT` are updater-only variables documented in the README and must not enter `src/schemas/env.ts`. The app stores what the updater reports in `Setting` `updater_status` and pending console requests in `updater_command`.
- `docker-compose.rm.yml` is an override file for `docker-compose.yml` or `docker-compose.au.yml` (`-f docker-compose.yml -f docker-compose.rm.yml`, or `COMPOSE_FILE` in `.env`), because the redaction model must combine with either stack; it is not a full copy like the updater stack. It gives `app` `LLMHUB_REDACTOR_URL: http://redactor:8080` and the `redactor` network and adds `redactor-fetch` (app image, `node redactor.mjs fetch`, the only redactor service with internet access, writes the `redactor-models` named volume, `restart: on-failure:5`, healthcheck disabled), `redactor-model` (`ghcr.io/ggml-org/llama.cpp:server-b<build>` pinned by build tag, user `65534:65534`, volume read-only, `--embeddings --pooling none`, context, batch, and micro-batch all `${LLMHUB_REDACTOR_WINDOW:-2048}` because the bidirectional encoder needs the whole window in one micro-batch, threads and `cpus` `${LLMHUB_REDACTOR_CPUS:-4}`, `mem_limit` `${REDACTOR_MEMORY_LIMIT:-4g}`), and `redactor` (app image, `node redactor.mjs`, user `node`, `node redactor.mjs --healthcheck`, 512 MB, one CPU). Both model services sit only on the `internal: true` network `redactor`, nothing publishes ports, and the app never waits for them. The runner creates `/models` owned by `node` so a new named volume is writable by the fetch service. The model weights live only in the volume, at the commit `LLMHUB_REDACTOR_REVISION` (40 hex, default in compose and `DEFAULT_REVISION`), never in the repo or image. `LLMHUB_REDACTOR_REVISION`, `LLMHUB_REDACTOR_WINDOW`, `LLMHUB_REDACTOR_CPUS`, and `REDACTOR_MEMORY_LIMIT` are compose values and must not enter `src/schemas/env.ts`; `LLMHUB_REDACTOR_MODEL_URL`, `LLMHUB_REDACTOR_MODEL_DIR`, `LLMHUB_REDACTOR_PORT`, and `HF_ENDPOINT` are read only by the adapter. A 2048 window peaked at 2.8 GB on CPU and 4096 at 4.4 GB; f16 CPU throughput was about 100 tokens a second on 4 cores. vLLM on a GPU (`perplexity-ai/PII-Tracer-vLLM`) behind an adapter that speaks the protocol is the documented GPU path; CI builds nothing extra because the adapter ships in the app image.
- `LLMHUB_REDACTOR_URL` is env because the compose overlay wires the redactor at deploy time: `ensureSystemCatalog` calls `ensureRedactorProvider` (`src/lib/bootstrap/redactor-provider.ts`), which upserts the internal `openai_compat` provider `llmhub-redactor` (base URL from the env, `enabled` and `internal` forced on), the model group `pii-tracer` (created once, never changed), and the deployment `llmhub-redactor-pii-tracer` on every start, and switches the provider off when the variable is unset. A sync failure only logs `redactor.provider_sync_failed` and never stops the start.
- `generate-env.sh` (bash 5) writes only the production `.env` for `docker-compose.yml`, using the same interactive generator as the other self-hosted services: `NODE_ENV=production`, `LLMHUB_TAG`, `NEXT_PUBLIC_APP_URL` (https origin), `LLMHUB_PORT`, `IP_MODE` (asks `proxy` or `cloudflare`; `--yes` also accepts `direct`), `POSTGRES_USER`, `POSTGRES_DB`, generated URL-safe `POSTGRES_PASSWORD` and `REDIS_PASSWORD`, generated `APP_SECRET` (64 hex characters), and the optional `SMTP_URL`/`SMTP_FROM`, `OIDC_CLIENT_SECRET`, S3 keys, and `LLMHUB_REDACTOR_URL` for a redaction service outside `docker-compose.rm.yml`. It writes atomically with mode 600, shows a masked summary, `--yes` takes defaults and environment variables as answers, and an existing file is replaced only with `--force`, which keeps its values (never a new `APP_SECRET` or database password) and leaves `.env.bak`. Local development copies `.env.example` (`NODE_ENV=development`, Postgres `127.0.0.1:5433`, Redis `127.0.0.1:6379`, RustFS keys). `LLMHUB_TAG`, `LLMHUB_PORT`, `POSTGRES_*`, `REDIS_PASSWORD`, and the `*_MEMORY_LIMIT` caps are compose values, not app env, and must not enter `src/schemas/env.ts`; `generate-env.sh` does not write the memory caps, operators add them to `.env` only to change the defaults.
- `APP_SECRET` is the only secret. `src/lib/crypto.ts` derives HKDF-SHA256 subkeys from it: `data` seals provider credentials, secret admin settings, and TOTP secrets and keys recovery-code hashes; `signing` (`signingSecret()`) signs session cookies, OIDC state, and Playground try-bearers; `updater` (`updaterKey()`) signs the messages between the app and the updater, which derives the same key from the `APP_SECRET` it receives. It must stay stable across deploys; rotating it invalidates sealed data and every session.
- S3 is optional (`src/lib/s3/`). Only the access keys come from env; provider preset, bucket, region, endpoint, prefix, addressing (`auto`, `path`, `virtual-hosted`, or `domain` for CNAME buckets), and public base URL live in Settings → Storage. Storage is active when a bucket and both keys are set; presets are data in `src/lib/s3/presets.ts`, and Test connection (`probeStorage`) writes, reads, and deletes one object under `llmhub-probe/` and returns a code, never provider text. Local RustFS uses the S3 keys from the generated `.env`.
- `SMTP_URL` is one `smtp://` or `smtps://user:pass@host:port` URL (`src/lib/mail/send.ts`). Without it password reset is off: the link is hidden and the route answers `RESET_DISABLED`. Reset links and tokens are never logged. The OIDC issuer, client id, scopes, and group rules live in Settings → Sign-in, only `OIDC_CLIENT_SECRET` stays in env.
- Optional Redis via `REDIS_URL` runs the in-process worker on BullMQ and shares RPM/TPM. Without it the same jobs run on a timer. Must not await Redis before Next binds. Must not require a worker sidecar.
- `BUILD_ID` is baked into the runner stage (`ARG BUILD_ID=development`); the CI pipeline passes the release version (`vYYYY.MM.DD.<sha>` or `dev-YYYY.MM.DD.<sha>`) as a build arg, and `/internal-api/version` reports it (`development` when unset; `currentBuild` / `buildInfo` in `src/lib/updates/build.ts`). The console sidebar footer shows it and, unless Settings turn `update_check` off, compares it with the GitHub releases of the same channel (`src/lib/updates/`, cached per process for six hours; the browser re-asks every six hours and on focus when stale) to show Update available. A browser whose loaded build differs from the served one is asked to reload (see [frontend.md](frontend.md)).
- The image `CMD` is `node migrate-deploy.mjs && exec node server.js`; there is no entrypoint script. `scripts/migrate-deploy.mjs` validates `NODE_ENV`, `DATABASE_URL`, and `APP_SECRET`, waits for Postgres, takes an advisory lock, and runs `prisma migrate deploy` then `prisma migrate status`, so a replaced image applies new migrations on every start. Only the container start migrates; locally run `npm run db:migrate`.
- The `Dockerfile` is multi-stage, and every stage builds on one exact Node release, `node:24.22.1-trixie-slim` (24.22.1 carries the October 2026 Node security fixes; a Node security release is applied by raising the tag, and Dependabot's Docker updates move it otherwise), without extra system packages (trixie ships `libssl3`; Next handles `SIGTERM` itself): `base`, `deps` (`npm ci --ignore-scripts`, because the root `postinstall` runs `prisma generate` and this stage has no schema), `prismacli` (production install of just `prisma`, `dotenv`, and `pg` from the lockfile with their install scripts allowed, so the schema engine is fetched at build time), `builder` (`prisma generate` + `next build`), and `runner`. The runner holds the Prisma CLI closure, the Next.js standalone output (including the usage PDF fonts under `src/lib/export/fonts/`, traced through `outputFileTracingIncludes`), `prisma/schema`, `prisma/migrations`, `prisma.config.ts`, `migrate-deploy.mjs`, and the updater (`updater.mjs` plus `updater/`); it deletes npm, npx, corepack, and Yarn from the base image first (nothing at runtime runs them, and npm's bundled packages carried every fixable HIGH image finding), and it runs as the image's `node` user with a Node `fetch` `HEALTHCHECK` on `/internal-api/health`. `next build` gets non-secret `DATABASE_URL` and `APP_SECRET` placeholders inline in the `RUN` because `src/lib/db/prisma.ts` validates env on import. The runner copies the optional BuildKit secret `antigravity_client_secret` (`RUN --mount=type=secret`, Google's public installed-app OAuth client secret for Antigravity sign-in) to `antigravity-client-secret` next to `server.js` (`root:node`, mode 0440, so the `node` user can read but not change it); without the secret (fork and Dependabot pull requests, a local `docker build`) the step writes nothing and the build still succeeds. That step must stay after `ENV BUILD_ID`: BuildKit leaves secret contents out of the cache key, and the per-build `BUILD_ID` makes it run again, so a cached layer never carries a stale secret or one from another build. The value must never become an `ARG`, an `ENV`, a build arg, or part of the repository; `.gitignore` and `.dockerignore` list `antigravity-client-secret`, so a local copy stays out of commits and the build context. Pass one to a local build with `docker buildx build --secret id=antigravity_client_secret,src=<file>`.
- `IP_MODE` must match how clients reach the app (trust model in [security-privacy.md](security-privacy.md)): `proxy` fits the compose deployment behind Caddy and needs the app port reachable only through a proxy that appends the peer to `X-Forwarded-For`; `cloudflare` needs the origin to accept web traffic only from Cloudflare's address ranges or a Cloudflare Tunnel; `direct` is for an app port that clients reach without a proxy (the compose files publish only `127.0.0.1`). A wrong mode makes throttles, key IP allowlists, sessions, and audit rows spoofable or puts every client into one bucket.
- CI: `.github/workflows/pipeline.yml` is the reusable (`workflow_call`) pipeline with inputs `channel` (`main` or `development`) and `publish`, the optional secret `antigravity_client_secret`, and jobs `version`, `quality`, and `image`. `release.yml` and `verify.yml` pass the repository secret `ANTIGRAVITY_CLIENT_SECRET` explicitly (never `secrets: inherit`), and `image` hands it to `docker/build-push-action` through `secrets:`, never `build-args`; fork and Dependabot runs get an empty value, which the action skips with a warning. `version` maps the channel once: `main` → `vYYYY.MM.DD.<sha>` plus `latest`, `sha-<sha>`, and the long sha; `development` → `dev-YYYY.MM.DD.<sha>` plus `dev`, `development`, and `dev-<sha>` as a prerelease; any other channel fails. `quality` runs against a `postgres:18-alpine` service: `npm ci` (its `postinstall` generates the client), `npm run migrations:check` against the pull request's base branch or, on pushes, the previous tip (`github.event.before`, fetched at depth 1), `prisma migrate deploy`, the drift check `prisma migrate diff --from-config-datasource --to-schema prisma/schema --exit-code`, `npm test`, `npm run test:integration`, i18n, styles, heroui, `tsc`, and lint. `image` builds `linux/amd64` on `ubuntu-24.04` and `linux/arm64` on `ubuntu-24.04-arm` natively (no QEMU) with per-architecture GHA cache scopes, then runs `scripts/smoke-image.sh` on the result: a throwaway Postgres and app container on a private network and a random loopback port, `/internal-api/ready`, `/internal-api/health`, `/internal-api/version` equal to `BUILD_ID`, `/internal-api/setup` 200, then a restart to prove migrate-on-start is idempotent; it prints the app log on failure. Trivy (`vuln` scanner, table output, `severity: HIGH,CRITICAL`, `ignore-unfixed`, `exit-code: "1"`) then scans the same image and fails the job before the digest is uploaded, so an image with a fixable HIGH or CRITICAL finding is never tagged and a pull request that introduces one fails. An accepted finding goes into a root `.trivyignore` (one ID per line, which Trivy reads from the working directory) with its reason recorded here; there are none today. Without `publish` the image is only loaded locally; with `publish` it is pushed by digest only (untagged, with provenance and SBOM), the smoke test pulls that exact digest, and the digest is uploaded as an artifact. `verify.yml` runs the pipeline on pull requests to `main` and `development` with `channel: ${{ github.base_ref }}`, `contents: read`, and cancels superseded runs; its `dependencies` job runs `actions/dependency-review-action` (`fail-on-severity: high`) and `npm audit --omit=dev --audit-level=high`, so a pull request cannot add a dependency with a known high advisory and fails while a production dependency has one; dependency review needs the repository's dependency graph, which is on together with Dependabot alerts. `release.yml` runs it on pushes to `main` and `development` with `channel: ${{ github.ref_name }}` and `publish: true` (`packages: write` for the build only), never cancels a running release, and then `publish` (`contents: write`, `packages: write`) joins both digests with `docker buildx imagetools create` under every tag and creates the GitHub release, and `scan` (`continue-on-error`) runs Trivy on the published digest and uploads every severity as SARIF to code scanning; it only reports, because the blocking scan already ran in `image` (with `format: sarif` the action reports all severities unless `limit-severities-for-sarif` is set, so a SARIF step cannot double as the gate). Nothing is tagged unless both architectures passed the smoke test, and no job is conditionally skipped. Jobs in `pipeline.yml` must not request permissions beyond `contents: read` (they inherit from the caller), and every job sets `timeout-minutes`. `codeql.yml` analyzes `javascript-typescript` and `actions` (the workflows themselves), one matrix job and category per language, on pushes and PRs to `main` and `development` and weekly. `.github/dependabot.yml` updates npm, GitHub Actions, and Docker weekly against `development`, grouping minor and patch updates. The repository has Dependabot alerts, malware alerts, and security updates on; GitHub opens security update pull requests against the default branch `main` and ignores `target-branch` and the groups for them, so after one is merged, `main` is merged back into `development`. Every third-party action is referenced by a release version tag (its moving major tag such as `@v7`, or the full release tag when the action publishes none, such as `@v5.0.0`); Dependabot moves the tags. `src/tests/docker.test.ts` checks the tags and the layout.
- `src/instrumentation.ts` validates the environment with `parseEnvironment`, ensures the system catalog on the Node runtime, then calls `startWorker` from `src/worker/boot.ts`. With BullMQ, `registerWorkerSchedules` (`src/worker/schedules.ts`) upserts the minute maintenance and two-hour `models` schedulers plus one deduplicated model sync at boot (skipped while the cached catalog is fresh); the local fallback runs the same two jobs on `setInterval`. Must not start workers during `next build` or on Edge.
- When `REDIS_URL` is set but Redis is unreachable at boot (ping through `sharedRedis` fails, or scheduler registration exceeds 10 s; BullMQ itself waits forever while Redis is down), the worker reports `unavailable`, runs the local timers, and retries BullMQ with exponential backoff (`bullmqRetryDelay`: 5 s doubling to 5 min). A successful retry stops the local timers, switches to `bullmq`, and logs `worker.mode_changed`.
- The local maintenance tick runs only after `claimLease("maintenance_sweep_lock", 55_000)` (`src/lib/jobs/lease.ts`, a `Setting` row holding the expiry like `model_catalog_lock`), so several replicas without Redis sweep about once a minute in total. The lease is not released after the sweep; it expires. A sweep can still outlive it (and BullMQ starts the next scheduled job on another replica while one runs), so retention deletes take their own `retention_sweep_lock` (50 s, released after the run) and stop after a 20-second budget; a large first cleanup finishes over several sweeps. The local model sync relies on `model_catalog_lock` and catalog freshness.
- Health: `GET /internal-api/health` (liveness, includes `worker.mode`). Ready: `GET /internal-api/ready` (Prisma read). Version: `GET /internal-api/version` (`BUILD_ID`, start time). There are no other health, version, or metrics routes; `/internal-api/live` (console stream) and `/internal-api/updater` (updater bridge) are not probes. On `SIGTERM` the server closes open live streams and refuses new ones so Next.js can finish its graceful shutdown.
- `README.md` is the operator guide: features, quick start, configuration reference, storage without S3 (Postgres `bytea`), backup and restore with `pg_dump` / `pg_restore` through `docker compose exec`, and upgrades by pinning release tags. Keep it in step with compose, env, and migrations.
- The repository has no license by design: `package.json` `"license": "UNLICENSED"` and the README License section reserve all rights. `engines.node` is `>=24`; there is no Prettier.
- There is no seed. The first account is created at `/internal-api/setup` (layout gate redirects home once any user exists; the action re-checks the count in a serializable transaction).

## Prohibited patterns

- Do not bake production secrets into an image. The bundled Google OAuth client secret is not one: it is Google's public installed-app client secret and enters only through the BuildKit secret described above.
- Do not document a host port that disagrees with compose `ports`.

## Commands

- `./generate-env.sh` (server) or `cp .env.example .env` (local)
- `docker compose -f docker-compose.dev.yml up -d postgres redis rustfs`
- `docker compose -f docker-compose.dev.yml up --build`
- `npm run db:migrate`
- `npm run dev`
- `npm run loadtest` (`scripts/loadtest/run.mjs`; `scripts/loadtest/` is kept out of the image by `.dockerignore`) load-tests a production build (`npm run build` first, with placeholder `DATABASE_URL` and `APP_SECRET` like the `Dockerfile`, or `--build <standalone dir>`) against a mock upstream and never reaches a real provider. It starts uniquely named `postgres:18-alpine` (with `pg_stat_statements`) and `redis:8-alpine` containers and the mock on random loopback ports (`--no-redis` skips Redis), migrates, seeds, runs `server.js` with `server-preload.mjs`, replays `--mounts subscription,api` over `--stages` (default `50:60,100:60,200:60`; `load.mjs` refuses more than 300 sessions, more than 1200 s per mount, and non-loopback targets), writes one JSON report per mount into a temporary directory (`--out` to choose one), and always stops its processes and removes the containers with their volumes, also on Ctrl-C. `mock-upstream.mjs` imitates Anthropic Messages, `count_tokens`, and the Claude OAuth endpoints and injects 429 and 529 with `Retry-After`, stream errors, disconnects, and long streams (`--error-429`, `--error-529`, `--retry-after`, `--stream-error`, `--disconnect`, `--long-rate`); `server-preload.mjs` (`NODE_OPTIONS=--import`, `LOADTEST_MOCK_URL`, `LOADTEST_METRICS_FILE`) sends the fixed Anthropic and Claude hosts to the mock, blocks every other outbound host, and samples memory, event-loop delay, CPU, and pg pool waits; `seed.ts` creates the owner, keys, mock Claude accounts, and `anthropic` keys (`--accounts`, `--api-keys`) through the app services; `load.mjs` sends the seeded model alias (`--model`, default `claude-load`, refused when the state file names another) and replays multi-turn Claude Code sessions with client aborts before the headers and mid-stream (`--abort-rate`) and reports throughput, TTFB and total latency, gateway overhead, stream validity, errors by type, turns served away from a session's account with or without a failure of that account, Postgres statements per request, and how the request log booked every abort. Measured in October 2026 on a shared 6-core host: one app process is CPU bound at about 27 to 31 requests per second (about 40 ms CPU per request with 100 to 250 KB Claude Code bodies), so 200 sessions wait about 3.4 s before the upstream, mostly on the ten-connection pg pool behind metering transactions that serialize on the shared team and org spend rows; no session left its account without a failure of that account, and with two `anthropic` keys short windows where both keys wait out a 429 answer 503 `overloaded_error` with `retry-after`.
