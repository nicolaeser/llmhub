# Operations

Load before changing `Dockerfile`, `docker-compose.yml`, `docker-compose.dev.yml`, `scripts/migrate-deploy.mjs`, `generate-env.sh`, `src/schemas/env.ts`, `src/instrumentation.ts`, `.github/`, or health endpoints.

## Mandatory rules

- Keep the environment minimal. `src/schemas/env.ts` is the only list: `NODE_ENV` (only `production` or `development`; any other value fails the start), `DATABASE_URL`, and `APP_SECRET` (min 32) are required; `NEXT_PUBLIC_APP_URL` defaults to `http://localhost:3000`; `S3_ACCESS_KEY_ID`, `S3_SECRET_ACCESS_KEY`, `SMTP_URL`, `SMTP_FROM`, `OIDC_CLIENT_SECRET`, `REDIS_URL` (trimmed), and `BUILD_ID` are optional. Read env through `env` from `src/lib/env.ts`, never `process.env.X` (except `NODE_ENV`, `NEXT_RUNTIME`, `NEXT_PHASE`); `redisUrl()` (`src/lib/jobs/connection.ts`) reads `env.REDIS_URL` and parses an explicit source with `envSchema.pick`. Must not add env vars for values that can be hardcoded or saved in Settings. A new variable also goes into `.env.example` (the local development template) and the README configuration table.
- Compose files hardcode the Postgres and Redis images (`postgres:18-alpine`, `redis:8-alpine`) and their ports; only the app image tag and host port take defaults (`LLMHUB_TAG`, `LLMHUB_PORT`). Data lives in bind mounts next to the compose file: `./postgres-data` at `/var/lib/postgresql`, `./redis-data` at `/data` (production Redis adds `--appendonly yes`), and `./rustfs-data` for dev RustFS. `postgres-data` and `redis-data` must stay in `.gitignore`, `.dockerignore`, and ESLint `globalIgnores`; must not switch back to named volumes (`src/tests/docker.test.ts`). Database user, database name, and credentials come only from the generated `.env`: `${POSTGRES_USER}`, `${POSTGRES_DB}`, `${POSTGRES_PASSWORD}`, and `${REDIS_PASSWORD}` in both files (Redis runs with `--requirepass` and `REDISCLI_AUTH` for its healthcheck), `${S3_ACCESS_KEY_ID}` / `${S3_SECRET_ACCESS_KEY}` for dev RustFS, without `:?` or defaults. The app service also loads `.env` through `env_file`; compose overrides `DATABASE_URL` and `REDIS_URL` with in-network hosts built from those values.
- `docker-compose.yml` runs `ghcr.io/nicolaeser/llmhub:${LLMHUB_TAG:-latest}` with `NODE_ENV: production` on `127.0.0.1:${LLMHUB_PORT:-3000}` behind a reverse proxy (Caddy) with Postgres and Redis on the internal network; only `LLMHUB_TAG`, `LLMHUB_PORT`, the `POSTGRES_*` values, and `REDIS_PASSWORD` are interpolated, the app reads `.env` through `env_file`. `docker-compose.dev.yml` builds `.` as `llmhub:dev` and publishes Postgres `127.0.0.1:5433`, Redis `127.0.0.1:6379`, RustFS `127.0.0.1:9000` / `9001`, app `127.0.0.1:3000`.
- `generate-env.sh` (bash 5) writes only the production `.env` for `docker-compose.yml`, using the same interactive generator as the other self-hosted services: `NODE_ENV=production`, `LLMHUB_TAG`, `NEXT_PUBLIC_APP_URL` (https origin), `LLMHUB_PORT`, `POSTGRES_USER`, `POSTGRES_DB`, generated URL-safe `POSTGRES_PASSWORD` and `REDIS_PASSWORD`, generated `APP_SECRET` (64 hex characters), and the optional `SMTP_URL`/`SMTP_FROM`, `OIDC_CLIENT_SECRET`, and S3 keys. It writes atomically with mode 600, shows a masked summary, `--yes` takes defaults and environment variables as answers, and an existing file is replaced only with `--force`, which keeps its values (never a new `APP_SECRET` or database password) and leaves `.env.bak`. Local development copies `.env.example` (`NODE_ENV=development`, Postgres `127.0.0.1:5433`, Redis `127.0.0.1:6379`, RustFS keys). `LLMHUB_TAG`, `LLMHUB_PORT`, `POSTGRES_*`, and `REDIS_PASSWORD` are compose values, not app env, and must not enter `src/schemas/env.ts`.
- `APP_SECRET` is the only secret. `src/lib/crypto.ts` derives HKDF-SHA256 subkeys from it: `data` seals provider credentials, secret admin settings, and TOTP secrets and keys recovery-code hashes; `signing` (`signingSecret()`) signs session cookies, OIDC state, and Playground try-bearers. It must stay stable across deploys; rotating it invalidates sealed data and every session.
- S3 is optional (`src/lib/s3/`). Only the access keys come from env; provider preset, bucket, region, endpoint, prefix, addressing (`auto`, `path`, `virtual-hosted`, or `domain` for CNAME buckets), and public base URL live in Settings → Storage. Storage is active when a bucket and both keys are set; presets are data in `src/lib/s3/presets.ts`, and Test connection (`probeStorage`) writes, reads, and deletes one object under `llmhub-probe/` and returns a code, never provider text. Local RustFS uses the S3 keys from the generated `.env`.
- `SMTP_URL` is one `smtp://` or `smtps://user:pass@host:port` URL (`src/lib/mail/send.ts`). Without it password reset is off: the link is hidden and the route answers `RESET_DISABLED`. Reset links and tokens are never logged. The OIDC issuer, client id, scopes, and group rules live in Settings → Sign-in, only `OIDC_CLIENT_SECRET` stays in env.
- Optional Redis via `REDIS_URL` runs the in-process worker on BullMQ and shares RPM/TPM. Without it the same jobs run on a timer. Must not await Redis before Next binds. Must not require a worker sidecar.
- `BUILD_ID` is baked into the runner stage (`ARG BUILD_ID=development`); the CI pipeline passes the release version (`vYYYY.MM.DD.<sha>` or `dev-YYYY.MM.DD.<sha>`) as a build arg, and `/internal-api/version` reports it (`development` when unset; `currentBuild` / `buildInfo` in `src/lib/updates/build.ts`). The console sidebar footer shows it and, unless Settings turn `update_check` off, compares it with the GitHub releases of the same channel (`src/lib/updates/`, cached per process for six hours; the browser re-asks every six hours and on focus when stale) to show Update available. A browser whose loaded build differs from the served one is asked to reload (see [frontend.md](frontend.md)).
- The image `CMD` is `node migrate-deploy.mjs && exec node server.js`; there is no entrypoint script. `scripts/migrate-deploy.mjs` validates `NODE_ENV`, `DATABASE_URL`, and `APP_SECRET`, waits for Postgres, takes an advisory lock, and runs `prisma migrate deploy` then `prisma migrate status`, so a replaced image applies new migrations on every start. Only the container start migrates; locally run `npm run db:migrate`.
- The `Dockerfile` is multi-stage, and every stage builds on `node:24-trixie-slim` without extra system packages (trixie ships `libssl3`; Next handles `SIGTERM` itself): `base`, `deps` (`npm ci`), `prismacli` (production install of just `prisma`, `dotenv`, and `pg` from the lockfile with their install scripts allowed, so the schema engine is fetched at build time), `builder` (`prisma generate` + `next build`), and `runner`. The runner holds the Prisma CLI closure, the Next.js standalone output, `prisma/schema`, `prisma/migrations`, `prisma.config.ts`, and `migrate-deploy.mjs`; it runs as the image's `node` user with a Node `fetch` `HEALTHCHECK` on `/internal-api/health`. `next build` gets non-secret `DATABASE_URL` and `APP_SECRET` placeholders inline in the `RUN` because `src/lib/db/prisma.ts` validates env on import.
- The client IP is the last `X-Forwarded-For` hop, the one the reverse proxy appends (`clientIp` in `src/lib/http/api.ts`). `X-Real-IP` and `CF-Connecting-IP` are never trusted. Throttles, key IP allowlists, and session records depend on this, so the app port must only be reachable through the proxy.
- CI: `.github/workflows/pipeline.yml` is the reusable (`workflow_call`) pipeline with inputs `channel` (`main` or `development`) and `publish`, and jobs `version`, `quality`, and `image`. `version` maps the channel once: `main` → `vYYYY.MM.DD.<sha>` plus `latest`, `sha-<sha>`, and the long sha; `development` → `dev-YYYY.MM.DD.<sha>` plus `dev`, `development`, and `dev-<sha>` as a prerelease; any other channel fails. `quality` runs against a `postgres:18-alpine` service: `npm ci`, `prisma generate`, `prisma migrate deploy`, the drift check `prisma migrate diff --from-config-datasource --to-schema prisma/schema --exit-code`, `npm test`, `npm run test:integration`, i18n, styles, heroui, `tsc`, and lint. `image` builds `linux/amd64` on `ubuntu-24.04` and `linux/arm64` on `ubuntu-24.04-arm` natively (no QEMU) with per-architecture GHA cache scopes, then runs `scripts/smoke-image.sh` on the result: a throwaway Postgres and app container on a private network and a random loopback port, `/internal-api/ready`, `/internal-api/health`, `/internal-api/version` equal to `BUILD_ID`, `/internal-api/setup` 200, then a restart to prove migrate-on-start is idempotent; it prints the app log on failure. Without `publish` the image is only loaded locally; with `publish` it is pushed by digest only (untagged, with provenance and SBOM), the smoke test pulls that exact digest, and the digest is uploaded as an artifact. `verify.yml` runs the pipeline on pull requests to `main` and `development` with `channel: ${{ github.base_ref }}`, `contents: read`, and cancels superseded runs. `release.yml` runs it on pushes to `main` and `development` with `channel: ${{ github.ref_name }}` and `publish: true` (`packages: write` for the build only), never cancels a running release, and then `publish` (`contents: write`, `packages: write`) joins both digests with `docker buildx imagetools create` under every tag and creates the GitHub release, and `scan` (`continue-on-error`) runs Trivy on the published digest and uploads SARIF to code scanning without blocking the release. Nothing is tagged unless both architectures passed the smoke test, and no job is conditionally skipped. Jobs in `pipeline.yml` must not request permissions beyond `contents: read` (they inherit from the caller), and every job sets `timeout-minutes`. `codeql.yml` analyzes `javascript-typescript` on pushes and PRs to `main` and `development` and weekly. `.github/dependabot.yml` updates npm, GitHub Actions, and Docker weekly against `development`, grouping minor and patch updates. Keep actions on their current major versions; `src/tests/docker.test.ts` checks the layout.
- `src/instrumentation.ts` validates the environment with `parseEnvironment`, ensures the system catalog on the Node runtime, then calls `startWorker` from `src/worker/boot.ts`. With BullMQ, `registerWorkerSchedules` (`src/worker/schedules.ts`) upserts the minute maintenance and two-hour `models` schedulers plus one deduplicated model sync at boot (skipped while the cached catalog is fresh); the local fallback runs the same two jobs on `setInterval`. Must not start workers during `next build` or on Edge.
- When `REDIS_URL` is set but Redis is unreachable at boot (ping through `sharedRedis` fails, or scheduler registration exceeds 10 s; BullMQ itself waits forever while Redis is down), the worker reports `unavailable`, runs the local timers, and retries BullMQ with exponential backoff (`bullmqRetryDelay`: 5 s doubling to 5 min). A successful retry stops the local timers, switches to `bullmq`, and logs `worker.mode_changed`.
- The local maintenance tick runs only after `claimLease("maintenance_sweep_lock", 55_000)` (`src/lib/jobs/lease.ts`, a `Setting` row holding the expiry like `model_catalog_lock`), so several replicas without Redis sweep about once a minute in total. The lease is not released after the sweep; it expires. The local model sync relies on `model_catalog_lock` and catalog freshness.
- Health: `GET /internal-api/health` (liveness, includes `worker.mode`). Ready: `GET /internal-api/ready` (Prisma read). Version: `GET /internal-api/version` (`BUILD_ID`, start time). There are no other health, version, or metrics routes.
- `README.md` is the operator guide: features, quick start, configuration reference, storage without S3 (Postgres `bytea`), backup and restore with `pg_dump` / `pg_restore` through `docker compose exec`, and upgrades by pinning release tags. Keep it in step with compose, env, and migrations.
- The repository has no license by design: `package.json` `"license": "UNLICENSED"` and the README License section reserve all rights. `engines.node` is `>=24`; there is no Prettier.
- There is no seed. The first account is created at `/internal-api/setup` (layout gate redirects home once any user exists; the action re-checks the count in a serializable transaction).

## Prohibited patterns

- Do not bake production secrets into an image.
- Do not document a host port that disagrees with compose `ports`.

## Commands

- `./generate-env.sh` (server) or `cp .env.example .env` (local)
- `docker compose -f docker-compose.dev.yml up -d postgres redis rustfs`
- `docker compose -f docker-compose.dev.yml up --build`
- `npm run db:migrate`
- `npm run dev`
