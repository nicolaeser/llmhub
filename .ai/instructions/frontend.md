# Frontend

Load before changing `src/app/`, `src/proxy.ts`, `src/i18n/` navigation, or Next.js/Tailwind/HeroUI configuration. Also load [STYLE.md](../STYLE.md) for visible work and [content-localization.md](content-localization.md) for copy.

## Mandatory rules

- This is Next.js 16 (exact version pinned in `package.json`). Before writing Next.js code, read the relevant guide under `node_modules/next/dist/docs/` completely. Do not edit the Next.js-owned block in root `AGENTS.md`.
- Request interception lives in `src/proxy.ts` (not `middleware.ts`).
- Keep the routing kernel on the route: `page`, `layout`, `loading`, `error`, `not-found`, `route`, `_action`. Route-only UI lives in that route's `_components/` folder (kebab-case). `src/components/<domain>/` is shared UI only after a second route imports it. Domain folders are lowercase.
- `page.tsx` stays a real page: auth, data loading, composition. Must not extract the whole page into a stub that only returns `<View />`.
- After a server action, update client `useState`. Must not use `revalidatePath` or `router.refresh`.
- Preserve `localePrefix: "never"` from `src/i18n/routing.ts`. Default locale is English; German overlays `lang/de`. There is no `[locale]` segment, so a next-intl `router.replace(pathname, { locale })` or `Link locale` never re-renders the root layout that holds `NextIntlClientProvider` and `<html lang>`; must not switch language that way. The user menu switches language with `setLocaleAction`, which writes `NEXT_LOCALE` with `LOCALE_COOKIE` (`src/i18n/locale-cookie.ts`: next-intl's name, `SameSite=Lax`, path `/`, one year, not `httpOnly` because `global-error.tsx` reads it); a cookie write in a Server Action makes Next.js re-render the page and its layouts in the new locale without a reload, keeping client state. `src/i18n/request.ts` reads that cookie before the proxy's `x-next-intl-locale` header, which still names the old locale during that render.
- HeroUI v3 compound components, `onPress`, and no `HeroUIProvider` are mandatory; see [STYLE.md](../STYLE.md).
- In-app navigation uses `Link` / `useRouter` from `@/i18n/routing`. File downloads use `<a href>`.
- Pages are `"use client"` and load data with their server actions through `useActionData` (`src/lib/hooks/use-action-data.ts`), which exposes `data`, `error`, `pending`, `reload`, `reloadWith`, and `setData` without setting state synchronously in an effect. Mutations return the new payload and the client replaces its state with `setData`. Must not use `router.refresh`, `revalidatePath`, or `revalidateTag`. The console's only server page is `src/app/(app)/page.tsx`, which redirects `/` to the user's console home.
- Must not create pass-through components that only return another component. A page composes its own markup; `_components/` hold parts with their own state or logic.
- Must not wrap pages in `Suspense` for search params. Read them with `useSearchParam` (`src/lib/hooks/use-search-param.ts`, `useSyncExternalStore`). Do not call `setState` synchronously inside `useEffect` (`react-hooks/set-state-in-effect`).
- Loading and pending states use HeroUI: `Skeleton` screens while a page, tab, or section loads, `isPending` with a render-prop `Spinner` on every async `Button`, and one transition per independent action. Before data arrives a page returns `PageStatus` (`src/components/console/page-status.tsx`) with the shape of its loaded view (`filters`, `tabs`, `stats`, `layout`; blocks live in `src/components/console/skeletons.tsx`): with a title it keeps the real `PageHeader` and only the body is a skeleton, and on failure it shows the title with a translated error `Alert` and Retry. Every console route has a `loading.tsx` that renders `PageLoading` with the same title and shape, so navigation, first load, and data never change the layout. Sections inside loaded pages, dialogs, and cards use `SectionLoading` (`list`, `details`, `table`, `charts`). A value that is not loaded yet renders as a skeleton (`StatCard` with `value={null}` or `pending`), never as a placeholder `0` or None that changes after the fetch; a reload for another query, page, window, or range shows skeletons instead of the previous numbers and rows, and a workspace switch clears `useActionData` so pages fall back to their skeleton instead of showing the previous company's data. `LoadError` shows a failed refresh above loaded data. Empty lists and searches without matches use `EmptyState`. Failed actions toast through `useErrorToast`.
- Error boundaries take the `retry` prop: `(app)/error.tsx`, `account/error.tsx`, and `providers/sub-add/error.tsx` (both link pages) render inside their layout with translated copy and the error digest. Every boundary, `global-error.tsx` included, passes the error to `reportClientError` (`src/lib/sentry/report-client-error.ts`) in an effect, which does nothing without `NEXT_PUBLIC_SENTRY_DSN`, because React keeps caught render errors away from Sentry's global handlers. `src/app/global-error.tsx` replaces the root layout, so it renders its own `html` and `body` without `NextIntlClientProvider`, the theme provider, or the stylesheet import: it reads `lang/*/GlobalError.json` through `createTranslator`, picks the locale from the `NEXT_LOCALE` cookie or the browser languages and the theme from the next-themes `localStorage` entry, and links home with a plain `<a href="/">` because the next-intl `Link` needs the provider.
- Form dialogs use `FormDialog` (`src/components/console/form-dialog.tsx`: HeroUI `Modal` around a `Form`, Enter submits, standard Cancel and pending submit footer, sizes `sm`/`md`/`lg`/`xl`). Confirmations use `ConfirmDialog`, either with a trigger child or with an overlay `state` from a menu action; `status` sets the tone and `focusCancel` puts initial focus on Cancel for actions that spend something irreversible (banked resets). Clipboard writes go through `CopyButton`. All console settings are one platform-only `/settings` page with `PageTabs` (`?tab=general|sign-in|storage|logging|cache|catalog`; Logging & alerts also holds the budget alert thresholds); each tab in `settings/_components/` loads and saves its own slice through `settings/_action.ts` and composes `SettingSection`, `SettingSwitch`, and `SettingText` from `settings/_components/setting-fields.tsx`.
- Shared security UI lives in `src/components/security/` (step-up dialog, second-factor input, TOTP enrollment, recovery codes, WebAuthn helpers).
- Every console section directory under `src/app/(app)/` (except `account`) has a `layout.tsx` that only calls `requireConsolePage` with its own path; a new section needs one and a `NAV` entry. Console navigation is `NAV` in `src/app/(app)/_components/nav-data.ts`. Every item has a `scope` (`platform`, `company`, or `both`) and a `permission` (a list means any of them); `canSee(permissions, item, scope)` and `visibleNav` filter by both, at most 13 items per scope. Platform: Organization (Companies, API keys, Console users), Gateway (Providers, Models), Policies (Guardrails, Knowledge bases, MCP servers), Insights (Usage, Logs). Company: Organization (Company, API keys), Policies, Insights. The `pinned` section (Settings, Developer) sits above the sidebar footer without a heading. Related screens are tabs of one page (`?tab=` through `useSearchParam`), not separate nav items: `/providers` (API providers, subscriptions, usage by key, account links, health), `/models` (catalog, groups, model presets), `/users` (users, roles), `/usage` (overview, markups), `/settings`, `/developer` (playground, API reference). A new console screen becomes a tab of the matching page before it becomes a nav item. `/` redirects to the first NAV item the user's permissions show in the current scope (`homePath(permissions, scope)`, falling back to `/account`), and retired console paths redirect through `redirects()` in `next.config.ts` to their tab (the removed `/assistant` and `/what-if` to `/`); must not recreate pages at those paths.
- Related screens share one route as tabs: `/models` (`catalog`, `groups`), `/keys` (`keys`, `templates`), `/users` (`users`, `roles`), `/usage` (`overview`, `markups`), and `/developer` (`playground`, `api`). The page renders `PageHeader` with its nav icon and `PageTabs` (`src/components/console/page-tabs.tsx`); the active tab lives in `?tab=` through `useTabParam` and other in-page params go through `setSearchParams` (`src/lib/hooks/use-search-param.ts`). `useTabParam` has no tab during server render, so `PageTabs` renders its tabs only on the client and a `?tab=` link never flashes the first tab. A tab whose permission or scope differs from the page's is hidden by the page's `_action.ts` (`grantedPermissions` in `src/lib/auth/guards.ts`, or a service such as `loadUsageTabs`); a single visible tab renders without the tab list. Each tab body is a `_components/<name>-tab.tsx` that loads its own data and returns `PageStatus` without a title while loading. Old paths (`/model-catalog`, `/model-templates`, `/roles`, `/markups`, `/playground`, `/api-ref`) are redirects, not pages.
- The console has two scopes, Platform and Company · {alias}; UI copy never calls them workspaces. `companyOf(session)` decides the scope: the owner's company view cookie (`src/lib/auth/workspace-cookie.ts`) or a company user's `User.orgId`. The `(app)` layout passes `consoleScopeOf(session)` (`src/lib/auth/console-scope.ts`) to `ConsoleScopeProvider` (`_components/console-scope.tsx`, read with `useConsoleScope`). `ScopeSwitcher` (`scope-switcher.tsx`, variants `expanded`, `rail`, `drawer`) sits under the brand: a Dropdown for the owner, a static company header for company users, nothing while no company exists. A switch calls `setWorkspaceAction`, then `notifyWorkspace` (`src/lib/auth/workspace-event.ts`) dispatches a same-tab event that reloads every `useActionData` and posts on a `BroadcastChannel` that other tabs relay; on a `platformOnlyPath` the company scope replaces the route with its home. `ScopedPage` in the `(app)` layout keys the page by scope, so filters, pagination, and selections start fresh in the new scope; the playground keeps its open session through `sessionStorage`. `/settings`, `/users`, `/providers`, and `/models` also redirect to `/` server-side through their `layout.tsx` (`requirePlatformScope`). Pages hide platform-only parts from the payload or the scope: the Companies page is the directory with Open company view in the platform scope and the company's own page (company name as `h1`, tree rooted at it, no Add company) in the company scope; Usage drops the company filter, company margin grouping, and the Markups tab; Guardrails shows only the overrides and the test tab; the API keys setup card is platform-only.
- The sidebar collapse state lives in the `llmhub_sidebar` cookie (`src/lib/utils/sidebar-cookie.ts`), which the `(app)` layout reads so the first paint has the right width. The footer holds the user menu (`user-menu.tsx`: Avatar trigger with account, language, theme, check connection, sign out), the collapse toggle, and a fixed-height status slot that shows the version or `BuildNotice`, so a late update check never shifts the layout. The top bar shows scope and page as `Breadcrumbs` from `md`; below `md` see [STYLE.md](../STYLE.md).
- Build status lives in `BuildStatusProvider` (`src/app/(app)/_components/build-status.tsx`), mounted by the `(app)` layout with the server's `currentBuild()`. It is the console's only live connection: an `EventSource` on `/internal-api/live` (see [api.md](api.md)). A stream without events for `LIVE_STALE_MS` (35 s) counts as lost; while lost it reconnects (every 5 s, later every 30 s) and probes `/internal-api/version` to tell Reconnecting from Offline. Only browsers without `EventSource` poll `/internal-api/version` every 30 s instead (constants in `src/lib/updates/build-change.ts`). It feeds the top bar badge (`live-badge.tsx`: Live, Updating, Reconnecting, Offline), whose popover shows version, uptime, and the updater (`updater-panel.tsx`, actions in `updater-controls.tsx`). When the served build differs from the loaded one (never for `development`), it shows a persistent toast with Reload and the sidebar footer keeps a Reload button; the footer also shows the current version, the Update available link from `loadUpdateStatusAction`, and Install (`install-update.tsx`, with a confirm dialog) when a connected updater has a new image. `auto-update-notice.tsx` offers to turn on automatic updates in a persistent toast while an updater is connected and they are off, so it never pushes the page down; closing it is remembered in `localStorage`. Settings → General has an Automatic updates section whose switch applies immediately instead of through the Save bar, because the popover and the notice change the same setting. Reload calls `window.location.reload()`: only a full document load picks up the new client bundle and server action ids, so it is not a `router.refresh` substitute and must not be used after mutations. The only other reload is an access change: `watchAccess` (`src/lib/auth/access-watch.ts`, registered by `BuildStatusProvider` with the layout's `sessionAccessKey`) reloads when the live `access` key differs from the loaded one, and when a failed action (`isActionFail` notifies `onActionFail`) answers `FORBIDDEN`, `PLATFORM_ONLY`, `INVALID_SCOPE`, `USER_PROTECTED`, `ROLE_PROTECTED`, or `Unauthorized` and `loadConsoleAccessAction` then reports a different key or no session; an unchanged key never reloads, so a page opened without permission keeps its error state.
- Live data rides on that same `EventSource`; there is no second connection. Components subscribe through `src/lib/hooks/use-live.ts` (`useLiveTopic`, `useLiveLimits(seed)` returning `{ items, removed }`, `useLiveRequests()`, `useLiveUsageToday(seed)`, `useLiveConnected()`), which wrap the `useSyncExternalStore` store in `src/lib/updates/live-client.ts`. The store counts subscribers per topic; when the wanted set changes, `BuildStatusProvider` reconnects once (after 300 ms) with `?topics=` and the server answers with a full state per topic, and a workspace switch reconnects too. Payloads are parsed and merged by the pure helpers in `src/lib/updates/live-events.ts`. Every live value has a seed from its server action so values never jump from a placeholder: limits merge by snapshot `version` (`mergeLimits`, `withLimitItems` for refresh results, removals from the stream win over older seeds), other topics take the newer `at` (`newestOf`). Pages fall back to their old polling only while `useLiveConnected()` is false. The Logs page reloads page 1 when a `requests` event names a new request (at most every 10 s) and shows a count of new requests with a jump to the newest on later pages (`countNewLogsAction`); the Usage overview shows a live Today card (UTC totals from `loadUsageTodayAction`, hidden while filters are set). The Subscriptions tab (`subscription-accounts.tsx`) seeds `useLiveLimits` with `loadSubscriptionLimitsAction` through `useActionData`: until the seed arrives the summary tiles show `Skeleton`s and each account row shows its Checking skeleton, never a placeholder count; afterwards rows and tiles follow the merged live snapshots. Refresh buttons call `loadProviderLimitsAction({ id, refresh: true })` or `loadSubscriptionLimitsAction({ refresh: true })` and merge the returned snapshots into the seed (`withLimitItems`); a failed refresh toasts and keeps the last limits, and an account's Refresh limits entry (row menu and details dialog) is disabled while the snapshot carries `retryAt`. Banked-reset redeems merge the returned `item` the same way, and imported accounts are refreshed one by one. When the live set names an account the provider list lacks, or removes one the list still shows as signed in, the tab reloads the provider list once per change (after 6 s, longer than the 5 s feed poll, so its own deletions do not trigger it). Without a live connection it re-reads the snapshots every 60 s while visible. The kind settings dialog (`provider-settings-dialog.tsx`) shows window kickoff (`window-kickoff-settings.tsx`) for `startsWindows` kinds with at least one account: a `Select` whose off entry uses the key `kickoff:off` instead of an empty id, saved through `saveWindowKickoffAction` into local state from the returned `kickoff`; the group header shows the choice as a chip. The Usage by key tab (`key-usage-tab.tsx`, shown only when `loadProviderConsole` reports `canSeeKeyUsage`) reuses the Subscriptions tab's `useAccountLimits` state for live window usage and loads per-key shares with `loadSubscriptionKeyUsageAction` through `useActionData`; it reloads them with the action and `setData` (no skeleton) when the `requests` topic names a new request or a snapshot `version` changes, at most every 10 s, and every 30 s while visible without a live connection. The view math is pure in `key-usage-view.ts` (`accountUsage`, `barSegments`): a key's part is the live `usedPercent` times its share, shares whose `since` predates the group's current window start are dropped, the top five keys get accent shades, further keys merge into one muted segment, and usage without matching requests shows as a muted outside-LLM-Hub segment.
- File uploads that feed a server-side job post `FormData` to a session-gated `/internal-api` route instead of a server action (MCP Anything uses `POST /internal-api/mcp/draft`); the route checks same-origin and the permission itself.
- A session opens its own page, `/logs/session?id=&key=&user=&tab=chat|requests` (`logs/session/page.tsx`, under the Logs layout guard and nav item; `sessionHref` in `logs/_components/log-export.ts`), not a Logs tab state. The page loads the session summary with `loadLogSessionAction`, renders the header, `Tabs`, and the Requests view (`session-trace.tsx`, which takes its data from the page), and mounts `SessionChat` (`session-chat.tsx`, own `useActionData` through `loadLogSessionChatAction`) only on the Chat tab; both refresh through `useLiveReload` while the session is active. The chat shows each message once, a divider for resent history with its cache share, collapsed reasoning, tool calls and results, attachment tiles, a footer per request, and later side threads in a `Disclosure`; it never renders images from stored content.
- Model output in request log transcripts renders through `Markdown` (`src/app/(app)/logs/_components/markdown.tsx`: `react-markdown` + `remark-gfm`) without raw HTML, and links pass `safeHref` (in-app paths or `http(s)` only).

## Architecture

- `src/app/(app)/` authenticated console.
- `src/app/account/` public account screens.
- `src/app/providers/sub-add/` public add-account link pages (`[token]` and `manage/[token]`, own layout outside the console). `src/proxy.ts` lets only `isSubAddPage` paths (`src/lib/http/public-path.ts`, a full 43-character token) through without a session; every other `/providers` path stays behind the console session.
- `src/app/internal-api/` private HTTP plus the first-operator page `setup/`.
- `src/app/api/v1/` and `src/app/api/subscription/` gateway; `src/app/api/mgmt/` management-key API; see [api.md](api.md).
- Colocated walk policy: `src/tests/route-view-policy.ts`.

## Prohibited patterns

- Do not add `src/middleware.ts`, `HeroUIProvider`, v2 flat subcomponents, `dark:` utilities, or overflow clipping.
- Do not put test-only walkers in `src/lib`.
- Do not add mapping-only wrappers.
