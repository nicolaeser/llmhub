# API

Load before changing `src/app/api/` (`v1/`, `subscription/`, `mgmt/`), `src/app/internal-api/`, `src/app/sso/`, `src/app/scim/`, health, metrics, or error responses.

## Mandatory rules

- The API has three mounts under `src/app/api/`: `v1/` (OpenAI- and Anthropic-compatible gateway), `subscription/v1/` (the same API on signed-in subscription accounts), and `mgmt/` (management API). Anthropic SDKs use `/api` and `/api/subscription` as base URL. `/v1`, `/subscription/v1`, and unprefixed management paths no longer exist; the `src/proxy.ts` matcher still skips `/v1` and `/subscription` so legacy clients get a 404 instead of a login redirect. Each endpoint is a `route.ts` that uses shared gateway helpers. Do not revive a barrel of handlers.
- The logical endpoint name stays `/v1/...`: `gatewayPath` (`src/lib/gateway/api-paths.ts`) maps `/api/v1/*`, `/api/subscription/v1/*`, and the legacy `/subscription/v1/*` of older log rows onto it. Key endpoint restrictions, log replay, and the OpenAI batch file `url` field use that name, so stored data needs no migration.
- `/api/v1` authenticates bearer tokens only through `authenticateBearer` (`src/lib/gateway/access/principal.ts`): virtual key, then playground try-token; management keys are rejected first. There is no master key, JWT, or custom-auth webhook; every caller is bound by model access, budgets, and rate limits. `verifyJwt` (`src/lib/auth/jwks.ts`) only verifies OIDC ID tokens for console SSO.
- `/api/v1` covers chat, completions, messages (Anthropic, plus `count_tokens`), responses (plus `input_items` and `input_tokens`), embeddings, moderations, OCR, audio, images, videos, files, batches (create, list, retrieve, cancel), models, and `systemone` (TypeSafe Jev decisions). Every verb forwards to a real upstream deployment; unknown aliases answer 404 and missing upstream endpoints pass the upstream error through.
- `/api/subscription/v1` serves only signed-in subscription providers (`codex`, `grok_build`, `claude`, `antigravity`) for chat completions, responses (create), messages, and models; every other path stays on `/api/v1`, which never routes to a subscription. On the subscription surface a model written `api/<alias>` runs on the API pool (`routeOf` in `src/lib/gateway/routing/route-pool.ts`): `withDeployment` resolves the pool per alias, so a `fallbacks` entry such as `api/<alias>` moves from plan quota to pay-as-you-go. `/api/subscription/v1/models` lists subscription models as they are and API models as `api/<alias>`, each with a `route` field. `api/` is reserved: aliases cannot start with it (`isReservedAlias`), usage, markups, and logs record the plain alias (`plainModel`), and `/api/v1` does not know the prefix. Both surfaces build these handlers from the same pool factories (`chatCompletionsRoute`, `createResponseRoute`, `messagesRoute`, `listModelsRoute`, `retrieveModelRoute` in `src/lib/gateway/endpoints/*-route.ts`) as `export const METHOD = factory("api" | "subscription")`; route files must not re-export each other. Anthropic clients use `/api/subscription` as base URL. It authenticates like `/api/v1`, is excluded from the `src/proxy.ts` matcher, keeps a separate response cache, and `/api/subscription/v1/models` lists only aliases with a subscription route.
- Responses and Messages convert through Chat Completions, except `/api/v1/messages` and `count_tokens` on `anthropic` deployments, which send the native body with the caller's headers. `anthropicPassthroughHeaders` forwards every client header except credentials, cookies, hop-by-hop, proxy and forwarding metadata (`x-forwarded-*`, `cf-*`, `x-real-ip`), and the hub's own `x-hub-*` and `x-llmhub-*`; Anthropic upstreams (`anthropic`, `claude`) receive all of them, other kinds only `anthropic-version` and `anthropic-beta`. On `claude` subscription deployments the client's own `user-agent`, `x-app`, and `anthropic-version` win over the gateway's Claude Code defaults, which apply only when the client sent none. A streamed chat that fails after the first byte ends with an OpenAI `error` chunk and `[DONE]` and is logged as a 502 error. Messages features with no chat equivalent (server tools, server tool blocks, `file`/`url`/`content` sources) answer 400 on other kinds. Token counting crosses over: `count_tokens` uses `/responses/input_tokens` on other kinds, and `/api/v1/responses/input_tokens` uses `count_tokens` on `anthropic`.
- Reasoning: chat `reasoning_effort` maps to adaptive thinking plus `output_config.effort` on Claude 4.6+ (`xhigh` becomes `high` before 4.7) and to `budget_tokens` on 4.5 and earlier. On xAI grok 4.5+ it is clamped to `low`–`high` (`xhigh` from 4.6). Claude thinking returns as `reasoning_content` plus signed `thinking_blocks`, which callers send back on assistant messages. Responses emit `reasoning` items whose `encrypted_content` carries the signed blocks and is shown only with `include: ["reasoning.encrypted_content"]`. PII redaction never edits signed thinking.
- Structured outputs map `response_format` `json_schema` to Anthropic `output_config.format` and back; `strict` tools pass both ways.
- Image generations and edits and audio transcriptions relay upstream SSE when `stream` is set and meter the event that carries `usage`.
- Batches run on the in-process worker: `validating`, `in_progress`, then `completed`, `expired`, or `cancelled`, with OpenAI-format output and error JSONL files. Supported endpoints are chat, responses, completions, embeddings, moderations, and image generations.
- Gateway `file_id`s from `/api/v1/files` inline as data URLs in Responses `input_image`/`input_file`, chat `file` parts, and JSON image edits (`images`, `mask`).
- `/api/v1/systemone` mirrors the TypeSafe HTTP API (`state`, typed `questions`, probabilities in `answers`), has no streaming, and meters `usage.input_tokens`. Like TypeSafe it answers schema violations with 422 `invalid_request`; every other `/api/v1` verb answers 400.
- Chat completions, Responses, and Messages (on `/api/v1` and `/api/subscription/v1`) add the MCP tools assigned to the caller and run them inside the gateway (see [backend.md](backend.md)). Chat answers carry only the final assistant message with usage summed over all steps and `X-Hub-Cache: BYPASS`; Messages answers drop MCP `tool_use` blocks; Responses list `mcp_call` items (`server_label`, `name`, `arguments`, `output`, `error`) and stream `response.mcp_call.in_progress` and `.completed` / `.failed`. A failure after streaming started ends chat streams with an `error` chunk and `[DONE]`, Responses with `response.failed`, and Messages with an Anthropic `error` event. Callers opt out with `X-LLMHub-MCP: off`. Responses history drops stored MCP calls whose tools the request does not offer.
- `fallbacks`, `fallback`, `tags`, and `tag` are gateway-only and are stripped before any upstream call.
- Model access is enforced with `allowModel` on every verb, including batches, and `modelChain` on every alias in caller `fallbacks`/`fallback` (403 `model_access_denied`). Permitted aliases include model-template matches. `/api/v1/models` and `/api/v1/models/{id}` expose only permitted aliases and also accept `x-api-key`.
- JSON bodies are capped at 32 MB and uploads at 100 MB (`src/lib/http/api.ts`), answered with 413.
- `/api/mgmt` is the management API for console resources (keys, model aliases, providers, organizations, teams, projects, members, budgets, usage, logs). It authenticates only management keys (`sk-mgmt-`, `ManagementKey`); `/api/v1` rejects them before any lookup. A key's permissions are its granted scope ∩ `MANAGEMENT_PERMISSIONS` ∩ the owner's current role (`src/lib/management/scope.ts`); the owner flag is never honored.
- Every `/api/mgmt` handler is `export const METHOD = managementRoute(permission, handler)` (`src/lib/management/http.ts`). Handlers validate with `src/schemas/management.ts` (strict, snake_case), call the domain services from `src/lib` under `runAsPrincipal`, and return `src/lib/management/serialize.ts` shapes (`object`, snake_case, `null` for unset references, lists as `{ object: "list", data }`). Must not duplicate service logic in routes, and must not import server actions.
- Tenancy and budget routes call the tenancy services (`src/lib/tenancy/structure.ts`, `src/lib/tenancy/budgets.ts`) and the lookup helpers in `src/lib/management/structure.ts` (`byId`, `byAlias`, `budgetHolders`). `organizations` are companies, `teams` are departments, and `members` are a company's people (not console users). Creating a team, project, or member requires `org_id`; `team_id` is optional on projects and members, and the company of an existing one cannot change (`ORG_LOCKED`). Keys take `project_id` or `member_id` (both answer `KEY_BINDING_CONFLICT`; neither makes an internal key). Budgets are addressed as `/api/mgmt/budgets/{entity_type}/{entity_id}` with `key`, `user`, `member`, `project`, `team`, or `org` (`UNKNOWN_ENTITY_TYPE` otherwise), plus `/temporary` for boosts; `GET /api/mgmt/budgets` needs `tenancy:read`, writes need `budgets:manage`, and a cap above a parent answers `BUDGET_EXCEEDS_PARENT`.
- `/api/v1` errors use the OpenAI shape `{ error: { message, type, param, code } }` with codes from `GATEWAY_ERRORS` and types derived from status (`src/lib/gateway/errors.ts`); throw `GateError(status, code, message, { param })` and answer with `gateResponse(err, req)` (`src/lib/gateway/access/gate.ts`), usually by wrapping the handler in `gatewayRoute` (`src/lib/gateway/endpoints/pipeline.ts`). `/api/v1/messages*` and any `/api/v1` request with `anthropic-version` get the Anthropic shape `{ type: "error", error: { type, message }, request_id }`. Upstream errors keep the provider `code`/`param` except on 401/403. Unknown failures answer `internal_error` without the original message.
- `/api/mgmt` and `/internal-api` errors are RFC 9457 `application/problem+json` (`type`, `title`, `status`, `detail`, `instance`, `code`, `request_id`, optional `errors` with JSON pointers) via `problemResponse` / `problemFromError` (`src/lib/http/problem.ts`); router errors map through `routerGateError` (`src/lib/gateway/core.ts`) exactly as on `/api/v1`. Codes are UPPER_SNAKE from `PROBLEMS` (`src/lib/http/problem-codes.ts`); add new codes there. `type` links to `/api-ref#error-CODE`. Every error carries `x-request-id`.
- Internal JSON uses `NextResponse.json`. Must not export `writeJSON`.
- `/internal-api/setup` is the only first-operator create path. Register, SSO, and SCIM return `SETUP_REQUIRED` when `User` count is 0.
- SCIM 2.0 lives under `/scim/v2` with the SCIM bearer token and `application/scim+json`: `Users` and `Groups` (collection `GET`/`POST`, item `GET`/`PUT`/`PATCH`/`DELETE`) plus `ServiceProviderConfig`, `ResourceTypes`, and `Schemas`. Every route is `scimHandler(name, handler)` (`src/lib/auth/scim.ts`), which checks the token first. Lists page in the database (`startIndex` from 1, `count` up to 200, default 100) and accept one `<attribute> eq "value"` filter: Users on `userName`, `emails.value`, `externalId`, `id`; Groups on `displayName`, `externalId`, `id`; anything else answers 400 `invalidFilter`. Users carry `externalId` (unique), `active` (false blocks and ends sessions), read-only `groups`, and legacy `roles` (template key, ignored while group rules exist). Groups carry `displayName` (unique), `externalId`, and `members` (`[{ value: userId }]`; `excludedAttributes=members` omits them); PATCH accepts `add`/`replace`/`remove` on `members`, `members[value eq "id"]`, `displayName`, and `externalId`, and unknown member ids are ignored. Membership changes re-apply the SSO group rules (`syncScimRoles`, `src/lib/auth/directory-roles.ts`). Errors use the SCIM error schema; 5xx never carries the internal message. The token is created, replaced, or revoked in Settings → Sign-in (`settings:manage`, every permission because group rules can assign `admin`, plus step-up), shown once, and stored as a hash in `Setting` `scim_token_hash`.
- OIDC is `/sso/login` and `/sso/callback`; the redirect URI is always `NEXT_PUBLIC_APP_URL` + `/sso/callback`.
- Session-gated console endpoints are not public contracts: log export `GET /internal-api/logs/export?kind=requests|spend|audit&format=csv|jsonl`, chargeback CSV `GET /internal-api/usage/chargeback`, usage PDF `GET /internal-api/usage/export`, API reference try-out `POST /internal-api/api-ref/try`.
- Log export accepts the console filters `model`, `status`, `endpoint`, `keyId`, `userId`, `pii=1`, `from`, and `to`, parsed by `parseLogFilters` and applied through the same where builders as the Logs page (`src/lib/gateway/request-logs/request-log-query.ts`). Request content appears only in JSONL, only with `logs:content`, at most 1000 rows, and each such export writes a `log.content_export` audit row.
- Sign-in runs as server actions in `src/app/account/login/_action.ts`. `/internal-api/account` keeps `register` (403 `REGISTRATION_DISABLED` unless Settings enable it and SSO-only is off), `forgot-password` (404 `RESET_DISABLED` without `SMTP_URL`, 429 `RATE_LIMITED`), `reset-password`, `logout` (POST, 303), and `expired` (clears a stale session cookie).
- Health is liveness (`/internal-api/health`). Ready probes Postgres with a Prisma read (`/internal-api/ready`). Version (`/internal-api/version`) returns only `BUILD_ID` (`development` when unset) and the process start time, uncached and unauthenticated; the console polls it as its single liveness and new-build check. Do not add top-level health, version, or metrics routes.

## Prohibited patterns

- Do not put session-cookie routes under `src/app/api/`, and do not put gateway handlers under `src/app/api/mgmt/`.
- Do not hand-build error JSON; use `gateResponse` or `problemResponse`.
- Do not skip `gateRequest` / PII / budget on new `/api/v1` verbs that consume models, and do not record usage without the traced principal.
