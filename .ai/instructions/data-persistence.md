# Data persistence

Load before changing `prisma/`, `src/lib/db/prisma.ts`, `src/generated/prisma`, or modules that write `User`, keys, tenancy, budgets, settings, or spend.

## Mandatory rules

- Prisma 7 with the `prisma-client` generator and `@prisma/adapter-pg` (`prisma/schema/`, `src/lib/db/prisma.ts`). The adapter gets our own pg `Pool`, which must keep `Client: SequentialClient` (`src/lib/db/sequential-client.ts`); [backend.md](backend.md) has the transaction rule behind it.
- Generate output is `src/generated/prisma`. That directory is gitignored; `npm ci` generates it through the root `postinstall`, and `npx prisma generate` refreshes it after schema changes (no `DATABASE_URL` needed).
- Schema lives in `prisma/schema/` (`main.prisma`, `auth.prisma`, `gateway.prisma`). Migrations live in `prisma/migrations/`.
- The operator model is `User` with one `roleId` and `isOwner`. `Role` stores a `permissions` string array and an optional `templateKey`. Auth state lives in `Session`, `UserTotp`, `RecoveryCode`, `UserPasskey`, `LoginChallenge`, `AuthCeremony`, `UserSecurityEvent`, and `ManagementKey` (`prisma/schema/auth.prisma`). An SSO session's provider link lives in `SsoSession` (one per `Session`, cascade delete; `issuer`, `subject`, `sid`, sealed `refreshToken`, `checkedAt`, `validatedAt` of the last successful check). `User.credentialsSuspendedAt` marks personal credentials disabled because access was removed at the identity provider. `User.emergencyAccess` marks an account that may sign in locally while sign-in or roles come from the identity provider. SSO and SCIM identity lives in `UserIdentity` (`issuer` + `subject` unique, `userId` + `issuer` unique, cascade delete; `appRoles` records that the last sign-in took the role from provider app roles), `User.externalId` (SCIM, unique), and `ScimGroup` / `ScimGroupMember` (cascade on group and user).
- Containers apply the complete `prisma/migrations` chain on every start through `scripts/migrate-deploy.mjs`, using only the bundled `prisma migrate deploy`. Prisma owns its advisory lock and migration records. The wrapper retries P1001/P1002/P1017 and the P2002 `nspname` race of two starts creating a non-public schema at once up to ten times, refuses P3005 without baselining, and never resolves or rewrites failed migration records. The existing supervisor starts the web server only after success and preserves the keeper fallback for older compose files. See [operations.md](operations.md).
- `RequestLog` keeps metadata only; `RequestLogContent` contains nullable request/response JSON, `truncated`, `createdAt`, and nullable `sizeBytes`, with composite primary key `(logId, createdAt)`, a cascading log foreign key, and indexes on `createdAt` and `sizeBytes`. Keep `RequestLog.contents` as a one-to-many relation so older clients still work; read with `take: 1` and use both key fields for deletion. There are no runtime partitions or raw-SQL exceptions.
- Compatibility transition `20261115145000_prisma_compatibility` is the sole new customized migration: one transaction locks the log parent before its contents, copies every body (including legacy/default/daily partitions and SQL-null versus JSON-null), preserves owner and table/column grants, builds the equivalent plain table, replaces the partitioned table, and removes `PolicyOverride_one_target`. A failed copy rolls the whole transition back. It needs temporary space for the copied table and indexes and blocks log writes during the copy. All 63 previously shipped migrations remain byte-identical; their historical custom SQL must not be rewritten or replaced with a new baseline.
- `20261115145340_request_content_size` is untouched Prisma output. New content writes measure UTF-8 JSON bytes in `src/lib/gateway/request-logs/content-size.ts`; old rows and old-image writes retain null `sizeBytes` and are backfilled in bounded batches by `content-storage.ts`. The `content_storage` maintenance job uses a lease and serializable size trimming, deletes oldest eligible content only, and keeps metadata, today/future rows, and compliance archive holds. Size trimming waits while any row remains unmeasured. Time retention remains in `src/worker/retention-sweep.ts`. The console reports logical payload bytes and pending measurements, not physical database size; PostgreSQL reuses deleted space without immediately shrinking files.
- `RequestLog` and `SpendEvent` are write-heavy. Their tenancy indexes pair the column with `createdAt` because the logs explorer, exports, dashboard p95, usage reports, and spend anomaly alerts filter a scope plus a time range and sort by `createdAt`: `RequestLog` `(keyId|userId|teamId|orgId|projectId|memberId, createdAt)` plus `createdAt` and `status`, and `(providerId, createdAt)` for per-key subscription limit attribution (migration `20261029120000_request_log_provider_index`); `SpendEvent` `(keyId|userId|orgId|projectId, createdAt)` plus `createdAt`, `model`, `teamId`, `memberId`. Replace a single-column index with the composite instead of adding both. `GatewayAuditLog` reads only by `createdAt`; `UsageDaily` reads by day ranges through its primary key, which leads with `day`.
- String status and kind columns stay `TEXT` validated in code; do not convert them to Postgres enums. Migrations run on every container start, and an enum cast fails on any unknown legacy value, which would stop the container from booting.
- Deleting a console user goes through `removeUserWithInternalKeys` (`src/lib/auth/user-removal.ts`, used by `deleteUser` and SCIM delete): one transaction deletes the user's internal keys, their `TempBudget` rows (`entityType: "key"`), and the user's own boosts, then the user (`isOwner: false` guard); the audit row records `revokedKeys`. Project and person keys stay with `userId` set to null.
- Money columns are `Decimal(20,10)`. `UsageDaily` is the per-day rollup keyed by day, key, team, org, project, member, user, and model; it is updated with an atomic upsert per request.
- Budget holders are `VirtualKey`, `User`, `Member`, `Project`, `Team`, and `Organization`, each with `maxBudget`, `spend`, `budgetDuration`, and `spendResetAt`. `TempBudget` rows (`entityType` `key` | `user` | `member` | `project` | `team` | `org`) are boosts; the maintenance sweep deletes expired ones.
- `Organization` is a customer company, `Team` its department, `Project` belongs to a company (`orgId`) and optionally a department, and `Member` is a person of a company (not a console user). `User.orgId` is a console user's company access scope (`null` is a platform user; `onDelete: Restrict`). Tenancy is denormalized: a key stores `orgId` and `teamId` copied from its project or member, and an internal key stores its owner's `orgId`. Company actions update those copies in the same transaction when a project's or person's department changes, and changing a console user's company updates their internal keys; any new write path must do the same. Deleting a project or member deletes its keys.
- `ModelTemplate` links to keys through `VirtualKeyTemplate` (`onDelete: Restrict` on the template, so a template in use cannot be deleted). Provider data-handling facts (`zdr`, `retentionDays`, `region`, `noTraining`) live on `ProviderConnection` and feed template matching. `ProviderConnection.internal` (default false, API-key kinds only; migration `20261021160000_provider_internal`) moves a provider's routes into the `internal` pool, which no HTTP surface serves (see [backend.md](backend.md)). `ProviderConnection.newModels` (`auto` | `active` | `disabled`, default `auto`; migration `20261026120000_provider_new_models`) is the provider's catalog mode for first-seen models; read it through `newModelMode`, which maps unknown stored values to the default. `ProviderConnection.maxConcurrency` (nullable: null follows the kind default, 0 is unlimited) and `adaptiveConcurrency` (default false) came with `20261103090000_provider_concurrency`. Request labels (migration `20261026130000_request_labels`): `RequestLog.labels` (`String[]` of `key:value`, GIN index, so the logs filter `has` compiles to `@>` and uses it), `Organization.labelKeys` (the company allowlist), and `UsageLabelDaily`, a separate rollup with the `UsageDaily` slice dimensions plus `label` and `value` (one row per label, day, and slice, so rows grow per label value rather than per label combination, and `UsageDaily` stays untouched), indexed on `(label, value, day)` and pruned by `usage_retention_days`. Prisma migrations cannot build an index `CONCURRENTLY`, so a GIN index on `RequestLog` blocks its writes while the container migrates on start. Agent sessions (migration `20261026170000_request_log_sessions`) add `RequestLog.sessionId`, `agent`, and `providerId` (text, default empty) with an index on `(sessionId, createdAt)`. Account access lives in `ProviderAssignment` (one nullable foreign key per scope: organization, team, project, member, or key, cascade delete, unique per provider and target) together with `ProviderConnection.restricted`; per-provider routing lives in `AccountRouting` (`kind` primary key), including the automatic banked-reset policy `autoReset` (default off), `autoResetPercent` (default 99), and `autoResetScope` (`pool` or `account`, `TEXT` checked in code; migration `20261019143000_account_auto_reset`). Subscription sign-ins live in `ProviderLogin` (1:1 by `providerId`, cascade delete) with sealed tokens, `status` `active` | `expired`, `version` / `leaseUntil` for refresh, and `refreshedAt` / `retryAt` / `failures` for the refresh schedule and backoff (migration `20261019210000_provider_login_refresh`); token refreshes never touch `ProviderConnection.updatedAt`, which model discovery uses for optimistic writes. Subscription limits live in `ProviderLimitSnapshot` (1:1 by `providerId`, cascade delete): `limits` and the banked-reset view `resets` as JSON, `resetsAt`, `error`, `fetchedAt` (last success; `null` after `forgetLimits` marks the kept limits stale), `checkedAt` (last attempt), `nextAt`, `retryAt`, `failures`, `loginVersion`, the fetch lease `leaseUntil` / `leaseToken`, and `version`, which grows with every content write and drives live change detection (migration `20261020100000_provider_limit_snapshots`); it is written directly, never through `ProviderConnection`, so `updatedAt` there stays untouched. Add-account links live in `SubAddLink` (`tokenHash` unique, `kinds`, `maxAccounts` null for unlimited, monotonic `added`, `expiresAt`, `restricted`, `manageable` (default true; false hands out no manage token, migration `20261028150609_sub_add_link_manageable`); a row exists only while the link is usable), its restriction targets in `SubAddTarget` (same nullable-foreign-key shape as `ProviderAssignment`, unique per link and target, cascade delete with the link), and each contributed account in `SubAddAccount` (1:1 by `providerId`, cascade delete with the provider, `manageHash` indexed and null once the contributor deactivated the manage link, nullable `linkId` set to null when the link is deleted, `label` copied from the link; migrations `20261019230000_sub_add_links`, `20261020000000_sub_add_link_lifecycle`, which deleted revoked links and dropped `revokedAt`, and `20261021200000_sub_add_manage_optional`). `AccountRouting.kickoffModel` (default `''`, which turns window kickoff off) and `ProviderLimitSnapshot.kickoffAt` (the last kickoff claim, null before the first) came with `20261027120000_window_kickoff`. `AccountRouting.refreshCap` (default 0, which reads every account on Refresh all) came with `20261113120000_account_refresh_cap`.
- `Setting` `enterprise` is one JSON document and `patchEnterprise` writes every field, so a stored value does not prove an admin chose it. Historical migration `20261020090100_retention_defaults` removed `log_retention_days` and `content_retention_days` unless a `settings.logging` audit row exists or any retention value differs from the old defaults; a save of the Logging tab counts as a choice. The later move to 7 days and a 5 GB `content_max_gb` (`src/lib/settings/retention-defaults.ts`) is the application transformation `adoptRetentionDefaults` (`src/lib/bootstrap/retention-defaults.ts`), run once at boot from `ensureSystemCatalog`: under the same choice rules it drops stored `log_retention_days` / `content_retention_days` of 30 and `content_max_gb` of 0, writes with a compare on the old value, and records the `retention_defaults_7d_5gb` `Setting` marker so a later explicit 30 or 0 survives pruned audit rows. Future default transitions must use the same kind of idempotent application transformation that preserves explicit choices; do not add data SQL to generated migrations. Retention deletes use `UserSecurityEvent (createdAt)` and `ToolExecution (startedAt)` (`20261020090000_retention_indexes`).
- Small operational state lives in `Setting` rows rather than tables: banked-reset claims and leases (`provider_reset:<providerId>`, `provider_reset_lock:<providerId>`, `provider_reset_auto_lock:<kind>`, `provider_reset_pool:<kind>`), the updater's last report (`updater_status`) and pending console request (`updater_command`), next to the existing locks such as `model_catalog_lock`, `maintenance_sweep_lock`, and `retention_sweep_lock`.
- Guardrail overrides live in `PolicyOverride`: one row per target (exactly one of `orgId`, `teamId`, `projectId`, `keyId`, each unique with cascade delete, enforced by `policyOverrideSchema`, the discriminated `PolicyRef`, and the single `savePolicyOverride` write service; the old database check was removed by the compatibility transition) with nullable JSON parts `pii`, `injection`, `secrets`, and `rules`; `null` inherits that part. Migration `20261026180000_policy_overrides` copied the former `piiPolicy` / `guardrailPolicy` columns of `Organization`, `Project`, and `VirtualKey` (a guardrail override became all three guardrail parts, so behavior stayed the same) and dropped them.
- Production has no manual seed. `ensureSystemCatalog` upserts the role templates once (`Setting` `role_templates_seeded`) and default settings at boot; it never creates users or credentials.
- Migrations are forward-only. `src/tests/support/legacy-migrations.json` pins all 63 shipped files by SHA-256, from `20261006000000_init` through `20261113120000_account_refresh_cap`. Never edit, remove, rename, reorder, or squash them. The compatibility bridge is a documented exception needed to retire legacy database-only features without losing data. Every regular migration after it must come from Prisma, byte-for-byte including generated comments, without added transactions, backfills, checks, functions, triggers, views, or extensions. New timestamps must sort after every existing folder; CI checks both order and unchanged base-branch SQL.

## Development fixtures

`npm run seed-dev -- --reset-local=llmhub_dev` runs `scripts/seed-dev.mjs`: validate the target, apply the complete migration chain through `prisma migrate reset --force`, check migration status, then run `scripts/seed-dev-data.mjs`. The fixture writer inserts one example company, two departments, two projects, and two directory people (`Member`), with budgets. It creates no `User`, credentials, provider connections, roles, or settings. Operators still open `/internal-api/setup`; `Member` is product data, not an operator.

The script requires `NODE_ENV=development`, `APP_SECRET` of at least 32 characters, a loopback PostgreSQL URL, and a dedicated database ending in `_dev` or `_development` with no `prod`/`production` segment. Only the public schema is accepted, connection overrides are refused, and `--reset-local` must exactly name that database. The command deletes all target data. Both the reset entry point and the direct fixture runner validate the target before database work. It must never be called from the image start, instrumentation, or production deployment. Tests live in `src/tests/seed-dev.test.ts`; setup gates and first-row concurrency are covered by `src/tests/first-admin-setup.test.ts` and `src/tests/integration/first-admin.test.ts`.

## Architecture

- Import the client from `@/lib/db/prisma`.
- Do not import Prisma into Client Components.

## Prohibited patterns

- Do not check in generated Prisma client.
- Do not add production seeds or run `seed-dev` at boot. The only reset/seed command is the local-only workflow above.
- Application code must use only the Prisma Client API. `src/tests/prisma-client-policy.test.ts` forbids raw Prisma queries, executes, unsafe variants, and TypedSQL throughout application source, with no allowlist. Migration SQL and database integration fixtures are separate from application code.

## Commands

- `npx prisma generate`
- `npx prisma migrate dev` for new SQL
- `npm run db:migrate` (`prisma migrate deploy`)
- `npx prisma migrate diff --from-empty --to-schema prisma/schema --script` to inspect the full schema SQL
- `npx prisma migrate diff --from-config-datasource --to-schema prisma/schema --exit-code` after `npm run db:migrate` to prove there is no drift (CI runs it)
